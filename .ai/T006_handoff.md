## 1. 最能回答你问题的三条真实论证链（T006-R 修正后）

你的问题是："之前的论文是怎么说明，他们有关网络（DCN）的工作与 Web 有关的？
我不能只说'网络是 Web 服务的基础'。"

**第一条，也是本轮唯一一篇 DCN 论文——`www24-inart`（WWW 2024 Research，DOI 10.1145/3589334.3645394）：**

> 深度学习已是许多 Web 应用的核心组件（点名电商、社交媒体、在线广告）`【作者明说】`
> → 这些模型参数多、训练慢（BERT 110M 参数，单机 >1.5 个月）`【作者明说 + 引用支撑】`
> → 分布式训练在 web infrastructure 中被广泛采用 `【作者明说 + 引用支撑】`
> → **作者在此再次点名 Web 应用**：计算加速后，是 "DL models employed in
> **web applications**" 的大模型带来 GB 级传输，于是瓶颈从计算转向通信 `【作者明说】`
> → 梯度压缩损精度、通信调度不减流量 → INA 减少送往 PS 的流量 `【作者明说】`
> → 现有 INA 都在单 PS 架构下，规模一扩大 PS 入口带宽就不够 `【作者明说】`
> → 因此需要"多 PS 架构 + 路由选择的 INA" `【作者明说】`

**位置**：Intro P1–P6，PDF p.1–2（作者稿版本）。
**⚠️ 验收 R1 更正（初稿写错了）**：初稿说"这条链在第 2 步之后分叉"——**判断过强，已撤回**。
原文 **P3 明确再次点名 web applications**，链条是**连续写的**。准确的表述是两点：

1. **适用范围**：P5 之后的前提是架构属性（单 PS 架构、路由目的地不确定），
   换成其他大规模分布式训练同样成立——这是"**非 Web 专用**"，不是"链断了"；
2. **未验证的边界**：实验负载是 **Cifar-10 图像分类**，**未验证具名 Web 服务与服务侧收益**。

换句话说：**Web 进入了动机层并支撑了瓶颈的前提，没有进入问题设定、方法与评价。**

**第二条——`www24-wise-start`（WWW 2024 Research，DOI 10.1145/3589334.3645393）：**

> 移动 Web 服务看重首屏内容，首屏可见内容的加载时间即 **First AFT**（Google 定义的指标）`【作者明说 + 引用支撑】`
> → 连接建立时协议必须探测网络，而**慢启动恰好负责首屏内容的加载** `【作者明说】`
> → 现行慢启动是"冷启动"：只用硬编码参数，即便参数随时间演进（CWND 4MSS→32MSS）仍是静态的 `【作者明说】`
> → 对该服务的自测：19.38% 的请求**发起于应用初始化后 1 秒内** `【作者本文实验】`
> → 但先验知识会因带宽波动和应用限速（application-limit）失效，所以必须继续探测 `【作者明说】`

**位置**：Intro 正文段落 P1、P3–P8，PDF p.1–2（P2 是脚注）。
**为什么它比 InArt 强**：第三句把"Web 指标"和"传输机制"**直接扣在一起**，
于是"改慢启动"就等价于"优化首屏"。**Web 进入了评价单位，而不仅是动机。**
**必须保留的限定**：生产环境测的是 **RCT**（降低 8.56%–16.15%）；
**First AFT 的 25.43% 来自 §4.3 的仿真**，且以"**被标记为首屏的请求的完成时间**"衡量
（不含页面渲染实测）。原文摘要与 P7 未做这个区分。

**第三条——`www26-starlink-cd`（WWW 2026 Research，DOI 10.1145/3774904.3792227）：**

> 互联网已从互联计算机演变为内容分发平台（55 亿人 / 每天约 330 EB / CDN 承担约 70%）`【作者明说 + 引用支撑】`
> → 多数 CDN 应用对时延敏感，要求请求由"最近"的缓存服务器服务 `【作者明说 + 引用支撑】`
> → CDN 把缓存部署在靠近用户的位置，并用请求映射技术（anycast / DNS 地理定位 / 动态路由）把请求导向最近缓存；
>   **在地面网络中，用户"通常"就近连到本地 ISP 托管的缓存** `【作者明说 + 引用支撑】`
> → **LEO 改变了这一点**：流量可能在数千公里外的 PoP 出口，使"用户在哪 / DNS 在哪解析 /
>   CDN 把谁判为最近"三者错位 `【作者明说 + 引用支撑】`
> → 具名案例：津巴布韦用户经 ISL 落到法兰克福 PoP（约 7000 km）→ DNS 按法兰克福选 → CDN 映射到欧洲缓存 → 跨洲回源 `【作者本文实验】`

**位置**：Intro P1、P3–P4、P6，PDF p.1–2（arXiv 2510.13710v1）。
**⚠️ 验收 R6 更正（初稿写错了两处）**：

1. 初稿说"CDN 请求映射隐含的前提是**用户离 PoP 近**"——**原文没有这句话**，
   原文说的是缓存邻近用户、以及"**CDN 基础设施到 PoP 的邻近度**"。PoP 是网络出口点，与缓存是两回事。
2. 初稿说"换成地面 ISP 接入，整个问题消失"——**错的**。原文自己报告
   **Benin / Madagascar 的地面 ISP 用户同样经海底光缆被送到欧洲的内容服务器**。
   正确的说法是：LEO 改变的是**出口位置与用户位置的解耦方式**，远端 CDN 路径本身两类网络都有。

**Don't**：不要引用该文的"PoP 距离解释最多 50% 性能方差"——本轮仍未在正文中找到对应支撑。

**一句话总结这三条**：桥不在"X 支撑 Y"（类别关系），而在**"具体对象 × 具体失效条件"**。
本轮共归纳出 **6 种桥接动作**，见 [argument_chains.md](../docs/conferences/WWW2027/web_relevance/argument_chains.md) §6。
