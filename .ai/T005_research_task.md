# Motivation

用户需要先决定论文怎样合理地建立 Web relevance。仓库已有 WWW 近三年网络论文的初步调研，
但本任务要推进到可复核的原文阅读：获取 PDF、转换全文、单独整理 Introduction，
逐篇拆解论证，再为我们的论文提出几种有实质差异的思路。

**本任务的研究对象是相关论文如何提出问题和建立 Web 关联，以及这种论证能否迁移到本项目。**
仅列论文、转述摘要、重复“网络支撑 Web”，均不足以完成任务。
“对该论文提出几个方案”在本任务中指为本项目 RPG-Recon 提出定位和 Introduction 方案。

# Research Questions / Hypotheses

1. WWW 近三年的 DCN／骨干网论文，如何从网络问题连接到具体 Web 系统、服务或研究问题？
2. 它们的 Web relevance 由什么支撑：任务定义、系统背景、实际依赖、工作负载、服务指标，
   还是只在动机中出现？不同论文的证据强度是否不同？
3. RPG-Recon 当前的设备传播解释图任务，可以沿用哪些论证步骤？哪些需要新材料或新实验？
4. 哪一种定位兼顾真实证据、科学贡献、研究投入和审稿可辩护性？

待检验假设：网络基础设施论文可能存在多种有效的 Web 关联方式，其中部分适用于当前项目。
允许结论为“目前只能支持较窄的基础设施定位”或“现有证据仍不足”，不能预设一定能证明契合。

# Scope and Execution

## 1. 检索与筛选

- 年份固定为 **The ACM Web Conference / WWW 2024、2025、2026**，不混入同名期刊。
- 核心范围为数据中心网络（DCN）、骨干网／WAN／跨数据中心网络中的测量、诊断、可靠性、
  传输、拥塞控制、流量工程等。候选必须实际研究通信网络，排除神经网络、社交网络等歧义。
- 优先完整检查三年的官方论文集／录用目录，再用 ACM DOI、作者主页、机构仓库、公开预印本补全。
  检索词应同时覆盖 datacenter、data center network、backbone、WAN、inter-datacenter、
  network measurement、transport、congestion、routing、fault diagnosis 等。
- 分别标注 Research、Industry、Companion、Workshop、Demo 等身份；主会 Research 作为
  投稿先例主证据，其他轨道可提供写作参考，但不能替代 Research 的契合证据。
- 微服务、容器／云运维、CDN、Web 测量等相邻主题单列。说明纳入它们的具体理由，
  不能因 DCN／骨干网结果少而无提示地扩大范围或凑篇数。
- 记录每年检索入口、日期、关键词、纳入／排除理由及无法访问项。同一工作的不同版本去重。
  摘要可用于初筛；是否纳入核心集及深读结论须以正文核验。
- 深读已确认的直接相关论文；另精选少量最有迁移价值的相邻论文作对照。先给清单和选择理由，
  然后自主继续后续步骤。直接相关论文稀少时如实报告，不设必须凑齐的篇数门槛。
- 核验当前 WWW 2027 Research CFP 对 Web relevance 的要求，保存官方来源及检索日期。
  区分官方要求、作者写法与我们的投稿解释；不从已录用事实推断录用原因。

## 2. 获取 PDF 与全文转换

对纳入深读集的每篇论文：

1. 获取可合法访问的完整 PDF，优先正式开放版本或作者／机构稿；保留正式书目信息与 DOI。
   核对 PDF 标题、作者、年份、版本与记录一致，排除同名论文、摘要页和错误下载。
2. 记录来源 URL、访问日期、版本、许可信息、文件名、页数及 SHA-256。
3. 转换为 UTF-8 TXT 或 Markdown，保留章节和可追溯的 PDF 页码标记。
   双栏内容恢复合理阅读顺序；去掉重复页眉页脚时保留原始抽取文件。
4. 检查第一页、Introduction 首尾、下一节边界及至少一个正文跨栏位置。
   有扫描页或抽取故障时再使用 OCR，并记录工具、命令、问题页和修复情况。
5. 抽取质量不合格不得标记“已读完”。缺失／不可获取论文保留失败原因，继续处理其他论文；
   优先改查作者公开版本，不绕过访问控制。

按用户此前要求，下载批处理、PDF 转换及相关程序在服务器执行；本地电脑仅用于任务和摘要协作。
执行前确认服务器及仓库位置；缺少必要连接／路径时一次性列出缺项，可先继续不依赖该环境的检索。
本任务不需要故障数据，不运行训练、推理、重评分或项目测试套件。

## 3. 单独整理 Introduction

每篇提供独立的 Introduction 文档，做到可与 PDF 对照：

- 标明论文 ID、准确标题、年份、轨道、原文节标题、PDF 页码范围。
- 原文段落依次编号 P1、P2……，明确起止边界；不得把 Abstract 当作 Introduction。
- 在许可允许或用户已提供原文的范围内，单独保存完整 Introduction 原文；
  其他情况提供结构化中文概要和页段定位。记录提取／展示状态，不把概要标作原文。
- 原文存档与自己的分析分开。面向共享的综合报告以原创分析为主，引用给出来源和页段，
  避免大段复制论文。不要用模型生成的补写内容修补缺字而不标记。
- 需要翻译时标为译文，保留术语与原文定位；翻译不能代替下面的论证分析。

## 4. 逐篇拆解作者的论证思路

每篇形成结构一致的中文分析卡，至少包含：

| 分析项 | 必须回答 |
| --- | --- |
| 问题定义 | 研究对象、输入、输出、使用者／受益者是什么？网络问题为何值得研究？ |
| Web 关联 | 明确涉及哪个 Web 系统／服务／基础设施需求？关联在引言哪一页哪一段出现？ |
| 段落作用 | 按 P1、P2……概述“背景→重要性→现有工作→缺口→挑战→洞察→方法→贡献”的实际展开；不要强套模板 |
| 现有工作与缺口 | 作者具体批评哪些能力不足？该缺口如何推出自己的方法？ |
| 核心洞察与贡献 | 区分任务定义、方法贡献、系统实现、工程规模和评价贡献 |
| 证据强度 | 引言里的收益由后文哪些数据／实验／指标支撑？哪些仅为动机陈述或推断？ |
| 与本项目的关系 | 可以借鉴的论证步骤、不能迁移的前提，以及与我们已有机制的潜在重合 |
| Reviewer 视角 | 若去掉 Web 术语论证是否仍成立？最可能被质疑的关联或贡献缺口是什么？ |

不要只读 Introduction 就断言全文已经验证服务收益。定向阅读任务定义、系统背景与实验段，
给出具体节／页／表位置。清楚标记“作者明确陈述”“全文实验支持”“本次分析推断”。
单篇分析建议控制在 800–1500 中文字左右，复杂论文可适度增加；质量优先于篇幅和数量。

## 5. 跨论文总结

形成横向对照矩阵，至少含：年份／轨道、网络层次、研究任务、Web 关联落点、
论证出现位置、支撑证据、技术贡献、可借鉴方式、迁移限制。

从证据归纳几种真实存在的引言组织方式，不预先强行指定分类。回答：

- 哪些论文依靠基础设施背景建立相关性，哪些进一步测量服务或用户侧效果？
- 哪些论证对 DCN 和骨干网分别适用？两种网络环境的前提有哪些差别？
- 哪些适合 RPG-Recon，哪些只是主题相近但证据条件不同？
- 现有 9/10 调研中哪些结论得到确认、需要收窄或需要更正？逐项列出依据。
- 最近邻工作的能力是什么，我们的问题定义与方法到底差在哪里？
  文献先例、写作技巧与科学创新分别讨论。

## 6. 为 RPG-Recon 提出至少三种方案

最终提出 **至少 3 个有实质差异的 Web relevance／论文引入方案**。
差异须体现主要问题、服务对象、论证链或所需证据，不能仅替换标题或添加 Web／LLM 术语。
基于前面的论文证据产生方案，不把旧文档的推荐定位当作必选答案。

每个方案交付：

1. 一句话定位，以及 2–3 句可讨论的英文 Web relevance 表述。
2. 5–7 段 Introduction 提纲：逐段说明目的、关键论点、承接关系和可引用论文。
3. 一段 200–350 中文字的开篇示例。已有事实直接写，缺失事实明确留待补证；
   不能把设想的真实事故、服务依赖或实验收益写成现有事实。
4. 如何自然引出单设备根、竞争起点、局部方向支持与传播解释 DAG；
   明确该方案保留了哪些现有问题定义，是否要求扩展系统或增加数据。
5. 支撑该方案的论文与具体页段；区分借鉴动机和借鉴技术。
6. “已有证据／必须补充／可选增强”表，给出最小补证任务和对应可检验假设。
   涉及实验时说明对照、混杂和潜在数据泄漏；本轮只设计，不执行。
7. 至少两条有力度的审稿质疑，以及可以用什么证据回答；
   无法回答时应如何收窄主张。
8. 给出定性投入判断：仅需写作调整、需补场景材料、需新增实验、或需改变研究范围；
   不编造人天或收益估计。

用一张表比较方案的 Web 关联强度、与现有证据匹配度、贡献清晰度、补证成本和审稿风险。
给出首选、备选及暂不推荐项，并解释取舍；所有方案证据均不足时允许暂不选定。
**本轮交付候选方案供用户／Work 讨论，不直接重写正式论文或宣布定位已最终确定。**

# Constraints

- 本任务仅限文献获取、阅读、研究分析与候选叙事设计；T001–T003 不自动启动。
- 尊重已有未提交修改和已删除文件；不修改算法、标签、评价协议、实验数字或已选正式稿。
- 不调用外部 LLM API 处理内部实验数据；本任务仅使用公开文献与已有脱敏项目说明。
- Pingmesh 异常不自动等于 HTTP 失败、SLO 违约或用户体验下降；没有证据的业务效果保留为待验证。
- 设备解释 DAG 与真实转发路径、干预因果图不同；不能为贴合论文先例而悄然更换输出语义。
- 不以“首次结合拓扑／时间”“前人只有根排名”等概括替代逐项最近邻比较。
- 下载、抽取、逐篇分析可并行或分批执行；共享清单与最终综合由一个负责人汇总。
  单篇失败须显式记录并继续其他工作，不能用摘要补成全文分析。
- 不自动提交或推送；交付可审阅的文档与命令记录。

# Acceptance Criteria

1. WWW 2024–2026 三个年份均有可追溯检索记录；DCN／骨干网核心集与相邻主题、不同轨道明确分开。
2. 每篇标记为“已深读”的论文具备身份核验、PDF、可读全文、独立 Introduction 材料及抽取 QA；
   获取失败、授权限制、提取失败、未读全文均明确列出，数量可对账。
3. Introduction 的页段位置可从 PDF 找回；不存在摘要冒充引言、双栏乱序未检查或生成内容冒充原文。
4. 每篇分析包含论证结构、Web 关联及证据强度，重要判断有页／节／表位置；不只是摘要合集。
5. 跨论文总结能回答“哪些论证适用及为何”，明确对旧调研的确认、修正和剩余不确定性。
6. 至少三套方案各有定位、英文表述、段落提纲、中文开篇、证据缺口、审稿质疑和投入比较；
   推荐理由同时考虑研究贡献与现有证据，不能仅因措辞更像 Web 而推荐。
7. 官方 CFP、论文原文、作者主张和执行者推断来源清晰；不虚构录用理由、生产案例或收益。
8. 本地链接、文档编码和文件清单检查通过；命令／工具／失败记录齐全，未运行项目实验。
9. 最终 HANDOFF 用简短结论引导用户先读方案比较，再按需追溯原文；本任务是否完成与定位是否获用户选定分别记录。
