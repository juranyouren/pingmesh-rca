# 用户真正要回答的问题

用户原话：“我需要知道，之前的论文是怎么说明：他们有关网络（DCN）的工作与 Web 有关的。
我在论文里不能简单地说，因为网络是 Web 服务的基础，所以就有关，太单薄了。”

**交付的主体必须是“作者在论文里怎样一步步把 Web 与这个具体网络问题连起来”。**
先还原作者实际写出的句子、承接和证据，再讨论我们能借什么。
不以概念科普、相关论文清单、Web 字频、强弱标签、CFP 范围或“请工程师补业务材料”代替答案。
不预设每篇好论文都有完整链条；原文若只停留在基础设施背景，就明确说到此为止。

# 核心工作一：逐篇还原作者的论证

每个重点样例依次交付以下内容。重点是准确解释桥接步骤，不另写一篇泛泛的论文综述。

## 1. 一眼能读懂的实际论证链

用 4–7 个短节点写出作者的链条，并给每一步原文锚点。例如：

具体 Web 应用/基础设施需求 → 某种工作负载或部署特征 →
它导致的网络约束/失效模式 → 已有机制缺口 → 作者研究的问题与贡献。

**这只是检查工具，不是必须填满的模板。**
作者可能先提出网络问题再回到应用意义，应先保留原文叙述顺序；
若为解释而重排，另标“分析者重排”，不能冒充作者写法。
缺少的中间步骤用“原文未建立”表示，不从常识补齐。

## 2. 关键句 / 句群对照表

为真正承担桥接作用的句子或句群编号 S1…Sn：

| 定位 | 原文短引或忠实中文释义 | 这句话在做什么 | 它如何承接上一句、推出下一句 | 依据归属 |
| --- | --- | --- | --- | --- |
| PDF 版本、页码、节、实际段落及可检索短锚点 | 引文、译文、概述分别标明 | 背景、需求、机制、失败、缺口、目标等 | 写出具体推理关系，不只贴标签 | 作者明说 / 作者引用他文 / 作者本文实验 / 分析者推断 |

共享报告使用必要的短引与原创释义，遵守许可和引用限制，不复制整段长文。
不能只有“P1 背景、P2 挑战”这种段落标签；读者应看到**到底是哪项前提推出哪项网络要求**。
若关键联系只在实验工作负载出现，而作者引言未解释，单列为“工作负载提供的联系”，
不能改写成“作者引言已经论证”。

## 3. 明确回答“比网络是 Web 的基础，多走了哪一步”

逐项回答：

- 作者所说的 Web 究竟是什么：应用、用户活动、平台组件、协议、内容交付体系，还是泛称？
- 哪项具体需求、流量/调用特征、部署方式或资源约束，使这个网络问题值得研究？
- 哪句话把这种需求推到了论文的**特定问题**，而非仅仅推出“网络很重要”？
- 对研究目标、问题设定、方法设计或评价，Web 场景分别产生了什么作用？
  只在动机起作用也可成立，应准确限定；不要求每项方法都必须 Web 专用。
- 作者是否连接到用户/服务效果？如果没有，实际停留在训练通信、流级性能、
  网络可靠性、诊断或其他哪层？不要把潜在受益当作已测收益。
- 若只剩一句基础设施背景，是否还存在可核验的部署/工作负载联系？
  都没有则直接承认，不能替作者写出一条更强的链。
- 对 RPG-Recon，最值得借用的**论证步骤**是什么，哪些前提不能迁移？

## 4. 有限度检查证据，不把任务变成全面挑错

只追到能够验证上述链条的背景、系统设计、实验及所引原始文献：
每一关键关联是引用支撑、动机断言、工作负载实例，还是本论文实际验证？
记录生产 / 测试床 / 仿真 / 代理指标的边界，以及推断跨越了哪一层。
性能数字非必要则不摘；使用时保留条件，特别避免 WiseStart 首屏仿真与生产结果混写。
按需核查关键上游引用，不递归扩成新一轮全领域综述。

# 核心工作二：从实际样例提炼“怎样写出具体关联”

在样例之后做横向比较，不沿用上轮四种强弱分类作为框架。

比较维度包括：Web 对象、使网络问题具体化的前提、桥接推理、
该前提进入了任务/机制/评价的哪一层、证据止点、作者留下的缺口。
归纳出的每种论证方式必须有原文例子；只有一个例子时不包装成普遍规律。
不同方式可重叠，不必排列成强弱阶梯，也不从录用事实推测被录用的原因。

重点区分三件事：
1. **作者如何表述相关性**；
2. **对象与工作负载实际提供了什么联系**；
3. **实验证明了什么效果**。

“算法去掉 Web 词仍然通用”不能作为不相关判据。
可作温和的替换检查：改成其他应用后，哪些前提仍成立、哪些目标/约束改变？
它用来界定适用范围，不能自动否定 Web 贡献。

# 核心工作三：把可迁移步骤接到 RPG-Recon

这一部分应晚于论文复盘，篇幅宜控制在两份核心报告正文总篇幅的三分之一以内。
不要求先有华为业务材料才能完成，也不预设 A+C 或机械凑三套定位。

基于最贴近的原文样例，提出 2–3 条候选论证链；证据不支持足够方案时宁可少给。
每条必须分别跨过：
**具体 Web/云场景需求 → 特定网络诊断困难 → 为什么要研究事故设备传播图。**
不能从“服务需要可靠性”直接跳到“因此需要我们的 DAG”。

每条提交：
- 对应论文 ID、原文步骤，以及迁移后每一步的依据；只借论证结构不冒充借到了实验事实。
- 5–8 句连贯中文论证草稿，标注“已有项目事实 / 可引用的一般事实 /
  待验证场景假设 / 本文研究目标”，标注可以放在句后，不打断正文。
- 具体指出它比“网络是 Web 基础”多建立了哪两项联系；若尚未跨过，明确断点。
- 为什么现有的根排名或其他诊断产物可能不足，哪些最近邻能力需核实；
  不概括为“前人只有根排名”，不将图形式不同当成贡献已经成立。
- 最小补证表：需要什么事实或控制、用来支撑哪句、缺失时删去/收窄哪句；
  如建议实验，说明假设、对照、混杂和泄漏边界，只设计不运行。
- 最有力的一条反对意见；现在能回答到哪里。

最终给出：现有证据下可写的部分，以及补到某项证据后才可增加的部分。
业务映射是一个可能的缺口，不能作为整份报告的主要结论或开始阅读的前置条件。
不宣称当前未知业务已出现 HTTP 失败、尾延迟/SLO 违约、人工效率或 MTTR 收益。

# Acceptance Criteria

1. 用户不打开 PDF 也能复述：某篇网络论文用了哪些具体前提，怎样一步步引出其问题；
   打开所标位置能够复核原文。
2. 至少一个完整展示的样例必须实际研究 DCN/云内部网络；其他层次与相邻工作标注清楚。
   文献数量不足如实报告，不以相邻工作替代。
3. 每条桥接推理能区分作者明说、引用依据、实验支持和分析者推断；不补写作者没有的链条。
4. 主报告明确指出代表论文比“网络是 Web 基础”多论证了什么；原文薄弱者也如实展示。
5. 三种证据维度分开，未因字频、通用性或未测页面指标判定无相关性。
6. 迁移建议引用具体论文步骤，显式保留未知业务，不从共同基础设施直接跳到设备图贡献。
7. 复用已有文件、定向补文与实际修复可对账；没有重复全目录检索或为凑数量扩大主题。
8. 本轮使用的页段、实验条件与来源信息经复核；必要补充程序在服务器执行；
   文档链接和编码检查通过，未运行项目测试或研究实验。

不改算法、标签、评分协议、正式论文或既有实验数字；不启动 T001–T003，
不调用外部 LLM API 处理内部数据，不自动提交或推送。
