# 故障传播路径还原调研与任务建议

更新日期：2026-08-11  
适用项目：Pingmesh 触发的数据中心网络根因定位

## 0. 已确认的任务决策

2026-08-11 已确认：

1. 主建模对象采用**设备级传播 DAG + 告警级证据**；
2. 可以投入工程师进行传播路径标注；
3. 评价指标暂不冻结为某一个指标，先保留完整的节点、边、顺序、候选路径和置信度信息；
4. 允许在公开且可复现的容忍规则或数值舍入规则下，直接按 case 计算路径准确率；
5. 后续选择指标时，应同时保留严格评价和容错评价，避免结果只依赖单一阈值。

## 1. 结论先行

建议把新增任务定义为：

> 在根因设备定位结果之上，还原一个**有证据支撑、显式表达不确定性的设备级故障传播骨架**；原始告警不直接作为主路径节点，而是先归一为告警事件/事件片段，再作为设备和传播边的证据。

具体建议如下。

1. **输出形式**：不要只输出一条线性链，也不要继续使用当前“根因设备 -> affected_nodes”的星形字典。主输出应是一个有向传播子图（通常为 DAG），同时从子图中抽取 Top-K 传播链供展示。
2. **评价指标**：暂不提前固定唯一主指标。候选指标包括设备节点/边指标、整路径匹配、路径编辑距离、Top-K 路径召回和直接的 case-level 路径准确率。没有路径真值时，只能评价拓扑合法性、时序一致性和证据可追溯性，不能把这些指标称为“还原准确率”。
3. **建模粒度**：采用“设备级主路径 + 告警级证据”的分层方案。当前项目的物理拓扑、根因标签和 Top-K 输出都是设备级，直接转成纯告警级路径会产生严重的重复告警、告警漂移和标注成本问题。
4. **论文表述**：在取得逐边路径真值前，应使用“传播骨架推断”“传播假设”或“证据支持的传播子图”，不要声称恢复了真实数据面路径或真实因果链。

## 2. 首先要区分三类“路径”

当前语境中至少有三种容易混淆的对象。

| 对象 | 含义 | 当前数据能否直接观测 |
| --- | --- | --- |
| 数据面转发路径 | 某次 Pingmesh 报文在 ECMP 下实际经过的设备/链路序列 | 不能；现有数据没有逐包 provenance 或完整路由轨迹 |
| 故障影响传播路径 | 物理故障或控制面异常从根因设备影响到其他设备及 Pingmesh 端点的过程 | 可部分推断，不能直接观测完整真值 |
| 告警传播链 | 各设备告警事件之间的时间、语义和依赖关系 | 有事件证据，但当前没有逐事件因果标签 |

本任务建议以第二类“故障影响传播路径”为主目标，以第三类“告警传播链”为证据，不把第一类“实际报文转发路径”当作可恢复真值。

传播方向统一定义为：

> 根因设备 → 中间传播设备 → 受影响设备/观测症状。

从症状向根因回溯只是诊断搜索方向，不能在输出中与传播方向混用。

## 3. 当前项目基础与缺口

### 3.1 已有基础

当前数据和代码已经提供了传播推断需要的一部分信号：

- Pingmesh source、sink 和触发时间；
- 设备级物理拓扑及设备角色；
- 设备告警/日志的名称、时间、严重度和描述；
- 部分描述中包含接口、对端设备、BGP、LLDP、local/remote fault 等关系线索；
- 拓扑排序、时序排序和融合后的设备级根因候选；
- Trust-Tree 对证据充分度和冲突状态的判断。

### 3.2 现有路径输出不是可评价的路径

当前提示词中的 `propagation_path` 实际是：

```text
根因设备 -> 一组 affected_nodes + 一段 impact 文本
```

它没有表达：

- 中间传播节点；
- 任意两个相邻设备之间的有向传播边；
- 传播顺序和边上时延；
- 每个节点/边引用了哪些原始证据；
- 多路径、分支和不确定性；
- 路径是否合法、是否可以复核。

因此它更接近根因解释摘要，而不是“路径还原”。

### 3.3 当前标签不能支撑路径准确率

现有 `label.json` 提供的是按 ranking 排序的根因/异常设备集合。当前评分代码取前若干标注设备计算 Top-1/Top-3/Top-5 命中。标签中没有：

- 有序的传播设备序列；
- 带方向的设备边；
- 多条可接受的 ECMP 等价路径；
- 根因、传播节点、受影响节点的完整角色标注；
- 告警事件之间的因果边。

因此，现有 159 个根因标注 case 可以继续评价根因定位，但不能直接评价传播路径还原。

## 4. 文献调研发现

### 4.1 不同工作使用了不同的“路径”表示

| 工作 | 路径表示与粒度 | 评价方式 | 对本项目的启示 |
| --- | --- | --- | --- |
| ProAlert, FSE 2025 | 从历史告警和系统拓扑学习传播模式，再验证在线告警的传播路径；主要服务于告警聚合和解释 | 论文主任务是告警/事件汇总 | 传播路径可以作为告警聚合约束，但“能解释”不等于“路径真值准确” |
| VOCE, 2025 | 节点是告警来源/系统组件，边表示相邻组件间推断出的传播方向；组件内部再选择起源告警 | 主要评价起源告警是否正确和耗时，未把边准确率作为主指标；案例中明确存在冗余边 | 与“设备级主图 + 告警级证据”高度相似，也说明只评价根因会掩盖错误传播边 |
| mABC, EMNLP Findings 2024 | 单条或多条服务级根因路径 | `PA=(P_c-τP_i)/P_t`，奖励正确路径并惩罚错误路径 | 可参考其正确/错误路径区分，但单一加权分数受 τ 影响，且不能呈现节点错、边错还是顺序错 |
| Stalled, Biased, and Confused, FORGE 2026 | 每个根因假设包含知识图谱上的传播路径 | Propagation Path Validity 只检查预测路径是否是 KG 中的合法 walk，并采用 Top-k | “合法路径”不是“真实路径”；本项目必须把 validity 与 accuracy 分开命名 |
| ErrorPrism, ASE 2025 | 从错误源到最终日志语句的完整函数调用序列 | 预测路径与人工真值**完全一致**才算正确；真值来自复盘报告和工程师逐路径核验 | 严格整路径准确率需要完整且高成本的路径真值，适合作为严格指标而非唯一指标 |
| FaultInsight, KDD 2024 | 动态指标因果图、关键传播链和时间对齐传播网络 | 主量化指标是根因指标排名，传播网络主要用于解释 | 若路径没有单独真值，必须诚实地把它定位为解释产物而非已验证还原结果 |

### 4.2 共同规律

1. 一个故障常常产生分支影响，因此图或树通常比单条链更自然。
2. 拓扑有效性只能排除不可能的边，不能证明因果关系。
3. 时间先后很重要，但告警采集延迟、聚合窗口和下游快速检测会导致“根因告警不一定最早”。VOCE 的真实数据分析也观察到只有约 45% 的起源告警最先出现。
4. 能做严格整路径准确率的工作，通常拥有代码级调用关系、逐路径复盘或人工完整标注；当前 Pingmesh 数据暂不具备同等真值条件。
5. 路径输出若没有边级评价，可能出现“根因设备正确但传播边大量错误”的情况。

## 5. 推荐的输出形式

### 5.1 主对象：设备级传播骨架

对每个 incident 输出有向子图：

```text
PropagationGraph = (V, E)
```

其中：

- `V`：参与本次故障传播解释的设备；
- `E`：设备之间有方向的候选传播关系；
- 一个设备可以是 `root`、`propagation`、`affected` 或 `uncertain`；
- 一条边必须同时记录关系类型、时间差、支持证据、置信度和不确定性来源；
- 图应尽量无环。若控制面关系形成环，可先按同一时间片/强连通分量聚合，再输出事件阶段 DAG。

建议的结构化 schema：

```json
{
  "direction": "root_to_symptom",
  "granularity": "device_with_alarm_evidence",
  "root_candidates": [
    {"device": "D1", "score": 0.86}
  ],
  "nodes": [
    {
      "device": "D1",
      "role": "root",
      "onset_time": 0,
      "confidence": 0.86,
      "evidence_ids": ["E1", "E2"]
    },
    {
      "device": "D2",
      "role": "propagation",
      "onset_time": 820,
      "confidence": 0.71,
      "evidence_ids": ["E3"]
    }
  ],
  "edges": [
    {
      "from": "D1",
      "to": "D2",
      "relation": "physical_link_impact",
      "lag_ms": 820,
      "confidence": 0.74,
      "evidence_ids": ["E1", "E3"],
      "alternatives": []
    }
  ],
  "ranked_chains": [
    {"rank": 1, "devices": ["D1", "D2"], "score": 0.74}
  ],
  "diagnosability": "partial",
  "unresolved_ambiguity": ["ecmp_equivalent_branch"]
}
```

论文或公开数据中应继续对设备和 case 匿名化。

### 5.2 为什么不能只输出单条路径

Clos/ECMP 场景中会同时存在：

- 多条物理可行路径；
- 一台根因设备影响多台邻接或下游设备；
- 控制面告警与数据面症状沿不同关系扩散；
- 观测不足导致的等价解释。

强行输出唯一线性链会把不可识别性隐藏成虚假的确定性。更稳妥的方式是先输出最小传播子图，再提供 Top-K 链作为阅读视图。

### 5.3 告警如何进入路径

不要把每一条原始告警都当成独立路径节点。先把重复的 active/clear、同类型刷量和同接口短时间重复事件归一为“告警事件片段（alarm episode）”，再用于：

- 证明某个设备在某个阶段出现异常；
- 证明相邻设备之间存在 local/remote fault、接口对端、BGP/LLDP 等成对关系；
- 提供节点 onset 和边 lag；
- 对模型生成的每条边做 evidence grounding。

必要时可另外输出事件级解释链，但它是设备传播骨架的下钻视图，不是当前阶段的主评价对象。

## 6. 推荐的评价指标

### 6.1 第一层：根因与角色正确性

继续保留现有指标：

- Root Top-1 / Top-3 / Top-5；
- Root MRR；
- 节点角色 Macro-F1：`root / propagation / affected / uncertain`。

这些指标回答“起点和节点角色是否正确”，不能替代路径评价。

### 6.2 第二层：有路径真值时的候选指标池

以下指标先作为候选池保留，待标注试点后根据路径形态、标注一致性和区分能力再确定主次：

1. **Device Node Precision / Recall / F1**：预测传播子图是否包含正确设备、是否引入过多无关设备。
2. **Directed Edge Precision / Recall / F1**：预测的带方向设备边是否正确。
3. **Exact Path Match Rate**：整条设备序列完全一致的 case 比例。严格但对 ECMP 和部分标注很敏感，应作为辅助指标。
4. **Normalized Path Edit Distance**：节点插入、删除、替换和顺序错误的归一化代价，用于区分“几乎正确”和“完全错误”。
5. **Top-K Path Recall / MRR**：当系统输出多条候选传播链时，评价可接受真值是否出现在前 K 条。
6. **Branch-aware Graph Score**：对存在分支的 case 直接计算节点集和边集 F1，不把传播图强行展平成单条链。

所有主指标应报告 case-level bootstrap 95% 置信区间，并按路径长度、设备角色、告警量、故障类型和 diagnosability 分桶。

#### 6.2.1 容错/舍入后的直接准确率

若希望最终结果使用直观的“准确率”，可以先为每个 case 计算预测传播图与任一可接受真值之间的相似度，再按公开的容忍阈值判断该 case 是否正确：

```text
s_i = max similarity(predicted_i, acceptable_gold_ij)
correct_i = 1[round(s_i, d) >= τ]
TolerantPathAccuracy = sum(correct_i) / N
```

其中：

- `acceptable_gold_ij` 是工程师标注的第 j 个可接受传播图或等价路径；
- `similarity` 可以由节点、带方向边、顺序和根因一致性组合，具体形式暂不固定；
- `d` 是统一公开的小数舍入位数；
- `τ` 是统一公开的正确判定阈值；
- `d`、`τ`、相似度组成和 ECMP 等价规则必须在测试集解封前确定；
- 同时保留未舍入的 `s_i`，便于后续复算和敏感性分析。

严格整路径准确率可以视为容错准确率的特例：只接受完全匹配，并令 `τ=1`。如果工程师只标出 definite/possible 边，匹配函数应允许 possible 边，但不能把 impossible 边计为正确。

这种设计可以直接给出易解释的 case-level accuracy，同时避免现在就把 Edge-F1、Exact Match 或某个加权公式定死。论文中必须同时公开容忍规则，并报告若干邻近阈值下的敏感性结果，防止通过阈值选择放大性能。

### 6.3 第三层：没有路径真值也能计算的“有效性”指标

以下指标适合第一阶段离线审计，但不能称为路径准确率：

| 指标 | 定义建议 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| Topology Validity | 预测边中可由物理拓扑或已知依赖关系支持的比例 | 边不是凭空生成 | 边真的发生了因果传播 |
| Temporal Consistency | 满足 `onset(v) >= onset(u)-ε` 的预测边比例 | 与允许时钟/采集漂移的时间方向一致 | 时间先后即因果 |
| Evidence Grounding | 能引用到具体输入告警/日志/接口证据的节点或边比例 | 输出可追溯、没有证据幻觉 | 引用的证据足以证明因果 |
| Root Anchoring | 传播图根节点是否落在正确根因设备集合中 | 传播解释起点正确 | 中间路径正确 |
| Observed-impact Coverage | 被传播图覆盖的高可信异常设备/端点比例 | 能解释多少已观测现象 | 未覆盖现象一定属于同一故障 |
| Compactness | 在达到给定覆盖率时使用的节点/边数量 | 是否避免输出整张拓扑 | 更小的图一定更正确 |
| Acyclic / Direction Validity | 输出是否满足定义的 DAG/方向约束 | schema 和算法约束正确 | 真实系统一定无环 |

### 6.4 第四层：不确定性与工程可用性

- Path coverage–risk：自动输出路径的 case 覆盖率与错误风险；
- Abstention rate：证据不足时拒绝给出唯一传播链的比例；
- Calibration：边置信度与实际边正确率之间的 ECE/Brier Score；
- 平均推理耗时、P95 推理耗时和内存；
- 平均图规模、平均证据数和输出 token 数；
- 工程师接受率、边级修改率和平均复核耗时。

## 7. 设备级还是告警级

### 7.1 设备级主建模的优势

- 与当前根因设备 Top-K 任务完全对齐；
- 物理拓扑边天然定义在设备之间；
- 当前标签至少能监督传播起点；
- 对重复告警和告警风暴更稳健；
- 输出更符合网络运维人员的定位与处置对象；
- 容易与现有 topo/temporal ranker、Trust-Tree 和 LLM 仲裁集成。

### 7.2 纯告警级主建模的问题

- 同一个物理事件会生成 active、clear、BGP、LLDP、route 等大量派生告警；
- 告警最早出现时间不等于故障最早发生时间；
- 告警名称和描述需要大量语义归一化；
- 单条告警可能包含对端设备信息，但当前没有事件因果真值；
- 标注量从“每 case 若干设备/边”膨胀为“每 case 数十到数百事件/边”；
- 论文主任务容易从网络故障传播偏移为告警关联或告警压缩。

### 7.3 推荐选择

采用两层表示：

```text
设备层：D1 ──▶ D2 ──▶ D3       （主传播图、主评价对象）
         │       │       │
证据层：E1/E2   E3/E4   E5      （归一后的告警事件片段）
```

即：

- 路径节点和边是设备级；
- 告警 episode 通过 `observed_on`、`supports_node`、`supports_edge` 关联到设备图；
- 设备内部的事件先后可以形成解释链，但不与跨设备主路径混为同一种边。

## 8. 真值标注建议

若论文要声称“路径还原”，需要新增一批路径标签。建议先做 30–50 个 case 的高质量试标，而不是立即重标全部 159 个 case。

### 8.1 每个 case 的最小标注内容

- 根因设备；
- 确定传播设备和受影响设备；
- `definite / possible / impossible` 三类设备边；
- 传播方向；
- 边类型：物理链路影响、控制面影响、仅时间相关、未知；
- 支撑边判断的告警/日志/接口证据；
- 是否存在多个可接受的 ECMP 等价路径；
- `fully_observed / partially_observed / unidentifiable` 可诊断性标签。

### 8.2 标注流程

1. 两名网络工程师独立标注；
2. 对节点集、边集和方向分歧进行仲裁；
3. 保存“确定边”和“允许边”，避免把不确定边强行做成唯一真值；
4. 统计节点/边 Jaccard、方向一致率或 Krippendorff's alpha；
5. 测试集标注在算法和阈值冻结后解封，避免路径标签泄漏。

如果工程师也无法根据现有材料确定唯一传播链，应把该 case 标为不可识别，而不是要求算法猜出一个唯一答案。

## 9. 可落地的方法草案

### 9.1 阶段 A：告警事件归一化

- 合并短窗口内同设备、同接口、同模板的重复告警；
- 配对 active/clear；
- 抽取接口、对端设备、BGP peer、LLDP remote、local/remote fault 等字段；
- 生成稳定的 `evidence_id`，保留到原始记录的 provenance。

### 9.2 阶段 B：构造 incident-conditioned 候选图

- 以 Pingmesh source/sink、物理拓扑和根因 Top-K 为条件裁剪搜索空间；
- 保留可行路径走廊、根因候选邻域和高可信异常设备；
- 不把 PageRank 高分直接解释为因果边。

### 9.3 阶段 C：设备边打分与定向

候选边只在拓扑相邻或有明确跨设备语义关系时产生。边分数可组合：

- 物理/逻辑邻接支持；
- local/remote fault、接口对端、BGP/LLDP 等语义配对；
- 带容忍窗口的相对 onset 与 lag；
- 根因候选和节点角色先验；
- 告警可靠度、去重后事件强度；
- 反向证据和替代路径惩罚。

### 9.4 阶段 D：传播骨架求解

可以把任务形式化为：在解释尽可能多高可信症状的同时，选择节点/边尽可能少、总边分数尽可能高的有向子图。工程上可先实现：

- 根因候选约束下的 beam search Top-K 链；
- 分支合并后的最小解释 DAG；
- 低分边裁剪；
- 存在等价解时输出多个候选而不是强制唯一解。

首版不必立即采用端到端 GNN。确定性的候选生成、边打分和图搜索更适合当前数据规模，也更易做消融和审计。

### 9.5 阶段 E：Trust-Tree/LLM 的新角色

- 确定性模块负责候选边、合法性和证据绑定；
- Trust-Tree 判断路径是否可诊断、是否存在等价路径或关键边证据缺失；
- LLM 只处理语义冲突、解释边机制或在候选边中仲裁；
- LLM 不得生成候选图之外的设备或无 provenance 的传播边。

## 10. 分阶段验收建议

### P0：定义与审计基线

- 固化术语、方向和输出 schema；
- 把当前星形 `affected_nodes` 输出升级为可解析的节点/边结构；
- 实现 Topology Validity、Temporal Consistency、Evidence Grounding；
- 在没有路径标签时明确标注为 validity evaluation。

### P1：小规模路径真值

- 试标 30–50 个分层抽样 case；
- 建立 definite/possible edge schema；
- 实现 Node-F1、Directed Edge-F1、Exact Match、Edit Distance、Top-K Path Recall；
- 先做人工规则/图搜索基线。

### P2：方法与消融

- 对比：拓扑最短路、仅时序、仅语义配对、拓扑+时序、完整方法；
- 消融：去掉接口对端、相对时间、告警去重、ECMP 多候选、Trust-Tree；
- 报告分路径长度、设备角色、故障类型和可诊断性结果。

### P3：工程价值

- 工程师盲评与边级修订；
- 复核耗时、接受率和错误边成本；
- 与只给根因 Top-K、只给自然语言解释进行对比。

## 11. 已确认决策与剩余开放项

### 11.1 已确认

- 采用设备级“故障影响传播 DAG”，告警作为节点/边证据；
- 开展工程师路径标注；
- 评价指标暂不定死，允许在公开容忍和舍入规则下计算直接准确率；
- 默认输出一个最小传播 DAG，并支持 ECMP/证据不足时的 Top-K 候选链和 diagnosability。

### 11.2 在标注试点后再确定

- 30–50 个首批 case 的分层抽样比例；
- definite/possible 边的实际分布及工程师一致性；
- case 相似度函数、舍入位数 `d` 和容忍阈值 `τ`；
- 最终主指标和辅助指标；
- 是否有足够 fully-observed case 支撑“路径还原”主张，还是需要同时保留“传播假设”子集。
