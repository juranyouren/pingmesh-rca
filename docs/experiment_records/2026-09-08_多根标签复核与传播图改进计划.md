## 2. 最高优先级：明确“多个根因”的标签语义

当前存在需要审计的解释差异：

- `Sys/RootCauseAnalyze/stage1/neural_graph.py:233` 的 `load_training_label` 从首个非空根因字段取第一个设备。
- labeler 的 `app.py:640` 会汇集 primary、secondary 等字段；`app.py:1389` 的初始化会将多个来源根设备设成多设备根因。
- 因此同一份来源标签可能被一个模块解释成“第一台是唯一真根”，被另一个模块解释成“多台共同为根”。是否已影响这 207 例，须统计原始字段才能确定。

先区分以下类别，不根据模型是否预测正确决定类别：

| 类别 | 需要记录的内容 | 处理方式 |
|---|---|---|
| 确认单根 | 唯一启动故障、对应证据与症状 | 保留单根定位与条件图任务 |
| 有证据支持的多根并发 | 每个独立根故障、发生时间、各自或共同解释的症状 | 标注根集合及多源传播图；不能仅取列表第一项 |
| 候选根集合仍不确定 | 多种可接受根集合及各自的支持/反证 | 保留多个根集合—图假设，不能误写成同时发生 |
| 一个根因及多个次生故障 | 起始故障与被影响设备的区别 | 次生故障设备不自动升级为独立根因 |
| 窗口内无关故障或多个事件被合并 | 时间窗口、症状关联和分组理由 | 判断是否应拆分 incident；保留追溯信息 |
| 链路或其他范围根因 | 原始证据及范围 | 单独分层，不强行改为设备根因 |

“多个设备均有告警”本身不证明多根；“多个根共同必要”也比“多个故障同时存在”更强。缺乏区分证据时保留不确定性，不虚构干预结论。

一个多根假设应绑定完整的 `根集合 + 传播边 + 症状归属 + 原始证据 + 不确定关系`。不同假设里的相反方向边不能简单取并集；共同下游节点则可以由多个根影响。物理连通不等于故障传播，跨越未观测中间层的解释需单列结构缺口，不能变成原始物理传播真值。

## 3. 第一项工程交付：labeler 的“复制 Case 详情”按钮

目标：一次点击即可复制可阅读的 case 文本，方便贴到对话中复核；大案例按块复制，不依赖文件下载、上传或外部服务。

### 3.1 第一版交互

- 在 case 顶部工具栏增加“复制 Case 详情”，简单模式和完整模式均可用。
- 默认生成协同复核版：原始观测、来源标签、当前草稿分节展示；来源标签和草稿明确标为“待复核判断”，不能混成客观证据。默认不附模型输出。
- 提供“仅原始证据”选项，用于独立判断；该模式不附已知根因、人工传播标签或模型预测，也不能通过派生事件表间接混入预测内容。
- 有预测读取权限时，允许显式附加模型对照；模型名称、运行版本与输出独立成节。
- 允许填写一句“本次疑问”，例如“D03 和 D07 是否都是独立根因，还是后者为次生影响”。
- 成功后显示字符数及复制范围。浏览器拒绝自动复制时，展示可全选的只读文本框供手动复制，不把失败提示成成功。
- 内容过长时自动打开分块面板；每块携带 case 标识、导出标识、版本、分块序号/总数。第一版可按约 12,000 字符分块，作为可调整传输参数，不当作模型 token 限额。

浏览器 `Clipboard.writeText` 受安全上下文与权限限制；服务器 HTTP 访问可能无法直接使用，应保留手动复制降级。参考 [MDN writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) 与 [Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)。

### 3.2 复制内容契约

| 内容 | 必要信息 |
|---|---|
| 来源与状态 | case/导出 ID、数据及标签版本、导出时间、当前 revision、草稿是否未保存、原文件名、导出范围与缺项 |
| 异常与观测 | source/sink、异常时间与时区或相对时间、症状、场景、观测窗口和缺失字段 |
| 原始根因记录 | 完整保留 primary/secondary/root_causes 等字段名称、顺序、设备 ID 和注释；不能只导出汇总后设备列表 |
| 设备及物理拓扑 | 稳定设备 ID、角色、端点锚点、原始边 ID、端口/peer、拓扑来源；明确区分原始、回退构造和展示推测关系 |
| 告警与日志 | evidence ID、所属设备、原始时间、事件名称、描述、端口及相关原始字段；保留无记录与未观测的区别 |
| 当前标签草稿 | 根范围与全部根设备、节点、DD/EE 边、确定/可能/排除/未知状态、证据引用、完整检查范围、备注、已有可接受假设 |
| 多根复核信息 | 各根的启动故障证据、时间、影响目标；“多根并发/次生影响/仍待确认”的判断来源 |
| 结构缺口 | 虚拟隐藏节点、手工中转、topology_overrides 等单列为展示辅助，不能混入原始邻接或真实传播边 |
| 可选模型对照 | 预测根集合/排序、图、相关分数与状态理由，明确标记为模型假设 |

第一版以完整内容分块为保障，不以无声截断解决体积问题。可提供摘要视图，但须列出省略的设备/事件数量及 ID 范围，并允许按设备或证据 ID 补充复制。稳定化名功能可选；如果启用，必须在拓扑、端口/peer、标签和文本引用中一致替换，并明确自由文本可能仍需检查，不声称自动完全脱敏。

### 3.3 实现位置与容易遗漏的行为

- UI：`pingmesh-propagation-labeler/src/propagation_labeler/propagation_labeler_ui.html`。复用现有 `state.bundle`、`state.label`、revision/dirty；点击时冻结快照，防止异步响应时串到下一 case。
- 数据：`app.py` 的 `/api/case` 已包含大部分拓扑和证据信息；现有 `/api/export` 只导出已保存标签，不足以支持本功能。建议新增独立只读导出处理及纯文本组装模块；草稿通过请求提交给导出处理，不写标签文件。
- 来源根字段目前被聚合，需保留原始 `label_v2.json` / `label.json` 片段及来源，才能分析主因/次因混淆。
- `state.label` 与 `bundle.label` 初始化时共享对象，不能把后者当不可变的原始标签；来源标签、已保存标签和当前草稿必须分开保存快照。
- UI 编辑 `nodes/edges`，规范字段 `device_nodes/dd_edges` 在保存时才同步。导出需基于当前草稿的实际编辑字段，在副本中生成一致视图，同时保留原始草稿；不能漏掉尚未保存的边。
- 复制不得调用 `saveNow`、自动完成标注、修复错误标签或触发重新推理。标签本来就可能有问题；即使校验失败也应能复制并附上错误信息。
- 预测视角的事件表可能来自模型 `event_nodes`；“仅原始证据”需从原始告警/日志构建中立内容，不能仅删除 `hypothesis_graph` 字段。

### 3.4 验收条件

1. 合成多根案例导出后，所有源根字段、草稿根设备、原始边 ID 和证据引用可追溯；primary/secondary 不被扁平化成同一语义。
2. 未保存节点/边修改、非法或不完整标签能够准确导出；导出操作本身不写标签、不增加 revision。
3. 切换 case、已有保存请求、读取冲突等场景下，导出的 case 与快照版本明确且一致。
4. 仅原始证据版不包含人工根标签、模型图或模型派生事件；展示虚拟节点不会混入物理图。
5. 中文长日志分块后可以按编号完整重组，字符不损坏、数据不静默丢失。
6. 自动剪贴板成功/拒绝/不可用三种场景均可交付文本；不依赖下载文件。

## 4. 协同复核：先 3–5 个案例，再固化规则

用户首先选择 3–5 个具有代表性的“疑似真实多根”case。我们逐案按下面步骤分析；这批案例用于形成标注规则，不用于估计全数据错误率。

1. 核对收到的块是否完整、来源/草稿版本是否一致；缺少关键证据时只请求对应设备或 evidence ID 的补充内容。
2. 从原始观测列出故障时间线、端点症状和各设备异常；证据缺失明确记为缺失。
3. 分辨独立启动故障、次生影响、无关并发故障；分别写出支持与反证，必要时保留多个根集合解释。
4. 在每个根集合假设下整理确定边、可能边、明确排除边和未知边；分别说明能解释哪些症状、剩余什么缺口。
5. 输出可复制的复核结论：建议根集合、逐边变更建议、证据 ID、未决项、与旧标签差异；不自动将 AI 判断写成真值。
6. 用户或工程师核验后在服务器保存新标注。争议保留为争议；建议增加第二位工程师复核部分案例并记录分歧。

固化规则后，在服务器对全部 207 例统计原始根字段、根数量、标签范围与冲突；复核全部高风险多根案例，并抽样复核单根/模型正确案例，避免只修改模型做错的标签。只需复制统计表和有争议案例，不要求传输整个数据集。

产出：根因与传播标注协议、案例分类统计、逐案修订记录，以及需要补充的日志/端口/时间证据清单。

## 5. 标签版本与评测修订

冻结现有 v1 根标签、传播标签、配置、fold、预测和代码版本/文件指纹；创建独立复核版本，不覆盖旧实验依据。每次修改记录根集合变化、边变化、原因、证据、复核者和日期。

先对旧预测在新评测口径下重评分，将“标签/计分修正”与“模型改进”分开。若根集合改变，Stage-1 的训练监督及 Oracle 输入也可能改变，后续需要重新训练/生成对应产物；若仅路径标签改变，P0 可先重评分，P4 等使用路径监督的方法才需要重训。现有单根预测不能靠事后计分变成完整的多根系统。

评测协议先确定再实现：

- 明确 `unknown`、已完整检查范围、`required` 与 `allowed` 的含义；未知不直接当负例，可选边不强制出现。
- 单根、确认多根、未决根集合、范围外案例分别报告数量、覆盖率和指标；不因难而静默删除多根案例。
- 多根主要报告根集合 Precision/Recall/F1、Exact-set、预测根数量；候选阶段同时给 any-root hit、all-roots recall 与逐根召回，不能命中一台就称全部根因正确。
- 多根图报告有向边和节点指标、各根/症状覆盖；多根 exact 要求根集合及相应传播结构匹配。若存在多个完整可接受假设，应对同一个根集合—图假设联合匹配，不能分别挑最有利根集合和边集合。
- 当前 `_root_score` 中集合有交集即成功、`uncertain` 返回成功的逻辑，不可直接充当多根 exact 或已确认根准确率。
- 全图 Strict exact 仅用于完整且可判定的图；部分标注报告已判定范围上的指标和覆盖范围，不伪装成全图恢复率。
- raw 与结构等价投影结果并列；统计空图、单边、多跳、分支图和投影前后规模。节点指标是否包含孤立根设备需明确。
- `unidentifiable` 按失败检查项分桶，再对照人工可观测性判断，不能作为标签直接使用。

若全部 207 例已参与多轮方法选择，将其作为开发/回顾性验证资料如实说明；争取新增时间段或站点的独立评测案例，不能把复核后随机划出的旧案例宣称为从未看过的测试集。

## 6. 多根方案的决策点与最小实验

完成代表案例复核与全量分类后，再决定方法范围：

- 若多根只是少量边界案例，可先形成可信单根主实验，同时完整保留多根挑战集及失效分析，并限定方法覆盖范围。
- 若多根是数据中的重要现象或论文要解决的核心问题，则主任务升级为根集合定位与多源传播图恢复；不能继续沿用单根 softmax 标签、Top-1 oracle 和单根解码来支撑整体结论。

升级多根时先做最小方案，不同时引入 LLM、复杂图模型与新解码器：

1. 根排序器改为支持多个真根的评分/集合选择；可先比较逐设备 sigmoid 的掩码监督与简单集合选择。未确认设备不自动作负例，阈值和根数量策略在训练侧开发集确定。现有单根 softmax 分数不能未经校准直接当多根概率。
2. P0 接收根集合，构建多源图，允许多个根影响共同症状。重审单根距离向外、根入度为零等假设是否适用。计算上若引入虚拟超级根，它不进入物理输出和真值计分；多源图也不必是互不相交的树。
3. 新增 root-set oracle：注入完整可信根集合，检查全根覆盖；这是一项新设定，区别于已经完成的单根 Oracle。对根集合仍不确定的案例不给出虚假的唯一 Oracle。
4. 固定相同预测根集合或真实根集合，比较简单拓扑/时间路径方法与 P0。先回答根集合恢复失败还是给定根集合仍无法恢复传播。

对已确认单根子集，补当前最有价值的控制：固定原始 Stage-1 Top-1，P0 只恢复图，不允许图分数改根。与已有普通 P0、candidate/direct oracle 比较。原 207 例旧标签下固定根应保持原 Stage-1 的 158/207；新标签或子集上必须重新计算，不能沿用 76.33%。

## 7. 何时继续优化传播图

完成可信标签与任务分层后，按错误分布选择一项改动：

| 被证据确认的问题 | 下一项实验 | 通过条件 |
|---|---|---|
| 无观测被当作无传播 | 显式区分 missing/unknown 与 explicit no-direct；受控删告警 | 固定根条件下改善已判定边指标，同时报告未知输出与覆盖变化 |
| 合法标注边被方向规则排除 | 先计算规则允许恢复的标签边比例，再单独放宽方向约束 | 恢复有证据的漏边，精度和结构有效性变化可解释 |
| 多根遗漏导致大片路径缺失 | 根集合定位及 root-set oracle 对照 | all-roots recall、根集合质量和图质量共同可解释 |
| 图选择器改坏根因 | 固定预测根与原图重排对照 | 没有独立证据支持收益时，图作为解释输出，不覆盖根集合 |
| 指标受聚合或空图主导 | raw/投影与图规模分层评测 | 明确非空、多跳、分支案例上的实际能力 |

不预设 F1 必须达到 0.8 或某个投稿门槛。改动应在冻结标签/评测版本、相同输入与划分下优于强简单基线，给出按真实 incident 分组的配对不确定性分析，并解释精度、召回和覆盖的取舍。标签改动带来的分数变化单列，不能记成方法提升。

暂缓：进一步 LLM rerank、图 MLP/P4 大规模调参、单纯扩大 Top-K。后续再补独立时间/站点泛化、运行开销和工程师排障用时/检查量实验；不从代理指标推断未经测量的 MTTR。

## 8. 执行顺序和交付物

| 顺序 | 工作包 | 验收/交付 | 依赖 |
|---|---|---|---|
| 1 | Case 复制 MVP；并行冻结旧结果 | 可复制的完整/分块案例；旧版本可追溯 | 无需先训练模型 |
| 2 | 协同复核 3–5 个多根代表案例 | 根集合及逐边证据建议、未决问题 | 复制功能可用 |
| 3 | 标注规则与全量 207 例根语义审计 | 单根/多根/不确定/范围外数量；复核标签版本 | 代表案例规则稳定 |
| 4 | 评测契约修订与旧预测重评分 | 根集合、图、完整度、raw/投影分层表 | 标签语义确定 |
| 5 | 决定单根主线+挑战集，或升级多根主任务 | 明确方法范围、适用案例与训练监督 | 全量审计结果 |
| 6 | 固定根控制；必要时多根 Oracle 与多源 P0 | 根定位/图恢复误差可分解的对照表 | 方法范围及评测冻结 |
| 7 | 针对主要错误做单因素改进 | 可归因的传播图改善与代价 | 逐例错误归因 |

本轮计划之后的第一项实施任务是“复制 Case 详情”及其回归验证；第一项研究任务是利用它复核真实多根案例。无需先开展新的全量模型实验。
