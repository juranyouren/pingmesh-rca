## 1. 论文解决的问题

在云服务系统中**重建错误的传播路径**。输出对象是**路径**本身，而非仅根因排名——
这是与本文输出对象最接近的跨领域工作之一。

## 2. 输入与额外观测要求

- 102 个**真实错误事件**（§III 数据集）。
- 真值构造：**事后复盘 + 与开发团队逐条源码逆向核验**（§III）。
- 是否要求 trace、拓扑或专门遥测 ⇒ 本轮未核实；按 T007 记录，输入条件与本文的
  Pingmesh 异常上下文不同。

## 3. 方法与输出对象

输出为**完整传播路径**，评价用 **Accuracy = 预测传播路径与真值完全一致的比例**
（§IV-A3 式 (2)），另有式 (3) Precision。**不是** edge-level P/R/F1。

## 4. 节点 / 边 / 时间尺度

- 节点：云服务系统的错误模板/组件（具体粒度本轮未核实）。
- 边：传播路径上的有向关系。
- 时间尺度：未核实。

## 5. 与 RPG-Recon 的重叠

- **输出对象同为传播路径/结构**，是本项目在 L2 场景中最直接的「输出对象孪生」。
- 真值来自人工复盘 + 源码核验，与我方依赖工程师标注的处境类似，
  其标注方法学值得借鉴。

## 6. 关键不同条件

- **指标口径**：exact-match Accuracy，路径级；我方主指标是逐案例宏平均**有向边 P/R/F1**。
- **难度比例（T007 R6 更正）**：原文 Fig.4 中 hop 0/1/2 分别为 **8/31/42**，总数 102。
  因此 **0–1 hop 占 38.2%**，0–2 hop 才占 79.4%。
  **T007 首轮「0–1 hop 近 80%」是错的**，不能据此弱化 exact-match 的评价难度。
- 场景为云服务系统，非 DCN 设备。

## 7. 可能的审稿质疑（对我方）

1. 「ErrorPrism 已经把传播路径作为输出并有真实事件评价，你的图恢复新在哪？」
   ——差异在：节点粒度（服务/错误模板 vs 物理设备）、输出（单条路径 vs 含分支与
   替代解释的 DAG）、指标（exact-match vs 边级 P/R/F1）、以及起点不确定性处理。
2. exact-match 在长路径上极难得分，**我方若主张边级指标更合理，需要正面论证**，
   不能只靠「exact-match 太难」这一印象——尤其考虑到上面的真实 hop 分布。
3. 人工构造参考路径的独立性：**是否盲标、标注者是否见过方法输出，原文未报告 ⇒
   未确认，不能自动保证无泄漏。**
