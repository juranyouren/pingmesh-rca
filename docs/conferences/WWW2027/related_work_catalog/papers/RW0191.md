## 1. 论文解决的问题（依据仓库既有记录）

生产规模网络中的**故障定位**。利用多源监控、设备分析、拓扑、全局时间线、
联合推理及历史知识更新，输出**错误设备排名及详细解释**。

## 2. 与 RPG-Recon 的重叠 —— **这是对我方威胁最大的 L1 工作之一**

- **已研究多源网络证据与跨设备故障定位**。
  因此按仓库既有结论（[Challenge 设计](../../Challenge设计：从普通根因定位转向故障图恢复.md) §6）：
  **不能声称「结合时间、拓扑进行 RCA」本身解决了新问题。**
- 使用真实生产网络数据与设备级推理，场景与本项目最接近。
- 仓库选型将其列为**优先外部定位对照**。

## 3. 关键不同条件

- **输出**：错误设备**排名 + 解释文本**，**不直接输出传播图**。
  选型结论：其输出不足以支持 Oracle-Graph / Full-Graph 列，相应格固定为 `X`。
- **模型条件**：原方法使用 LLM 与历史知识；本项目实验**不得调用外部 LLM API**，
  适配版必须披露模型、提示与输入缺项。
- 仓库现有 `Baseline/BiAn/bian_pipe1.py` 明确为 **minimal Pipeline1**，
  缺少拓扑、全局 timeline 等关键过程，且默认按告警数截取 6 台设备。
  **不能把 Pipeline1 称为完整 BiAn。**

## 4. 可能的审稿质疑（对我方）

1. 「BiAn 已在 SIGCOMM 2025 用生产网络数据 + LLM 做设备级故障定位，你的贡献边界？」
   ——必须承认其在「结合多源证据跨设备定位」上的优先性；我方差异只能建立在
   **输出对象（可逐边评价的传播 DAG）** 与 **起点不确定性下的条件重建** 上。
2. 「你用的是简化版 Pipeline1，比较是否公平？」——须报适配前后差异，
   且不得以 Pipeline1 的结果代表原方法。
3. **该文的存在直接限制了本文 novelty 的表述范围**，related work 必须正面处理。
