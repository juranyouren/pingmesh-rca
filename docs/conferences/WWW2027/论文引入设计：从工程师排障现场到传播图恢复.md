# 论文引入设计：从工程师排障现场到传播图恢复

更新：2026-09-16。本文档同时保存 PPT《pingmesh治理》的新版示意案例和旧的合成 `DEMO_001`。目前没有真实现场记录；所有操作、恢复顺序和收益均为待验证设计，不是用户研究、生产事故或人工效率实证。

## 1. PPT A/B/C/D 案例：根排名之后仍有决策问题

PPT 给出一个简化的四设备关系：A→B，B→C，B→D。其意图是说明一次事故中可能存在一条上游—下游解释结构；它不是从仓库数据读取出的真实传播图，也不是最终标签。PPT 同时示意一个设备排名 **A、C、D、B**，以及处理 A、B、从“4 devices inspected”到“2 devices handled”的对比。

| PPT 元素 | 可直接采用的陈述 | 不能直接断定 |
|---|---|---|
| A→B→{C,D} | 用作传播关系可能帮助组织检查/恢复顺序的示意 | 箭头已由真实事件证明，或一定对应原始拓扑邻接 |
| 排名 A,C,D,B | A 已排第一，所以研究问题不是“把 A 排到第一” | 图恢复改善了根定位 |
| 处理 A、B | 用作动作选择的示意对照 | A、B 是确定且唯一的恢复序列；B 必须处理的原因 |
| C、D 状态 `Established` | 按 PPT 原文记录该状态标签 | `Established` 本身证明 C/D 异常，或应改写为 Idle/reset |
| 4 inspected → 2 handled | 只作为图示计数，且检查与修复分开 | 50% 效率提升、MTTR 降低或成本收益 |

真正可检验的问题是：在相同初始排名、观测、反馈和权限下，传播关系是否能帮助先检查或恢复更有解释力的设备，并在满足停止条件后减少冗余动作。A 已经是第一名时，增量价值来自动作组织，而不是根排名改善。A 修复后 B 仍需处理的依据、C/D 的状态转换、自动恢复延迟、残留异常和基线是否允许停止，PPT 没有提供，正文必须保持开放。

### 建议的图稿分区

左侧放 Pingmesh 异常与设备状态，中部放平面排名和传播关系假设，右侧并列“仅按排名检查”和“在相同反馈下使用图解释”的动作流程。图例必须区分观测、候选关系、人工动作和推断；A→B→{C,D} 标为 illustrative hypothesis。不要把 4→2 画成已测量的性能柱状图，也不要把检查箭头误画成设备传播边。

英文图注草稿：

> **Illustrative decision value after root ranking.** The schematic assumes a candidate relation A→B→{C,D} and a ranking A,C,D,B. Because A is already ranked first, the possible benefit of a propagation explanation concerns action ordering and stopping, not root-ranking accuracy. The counts “four inspected” and “two handled” are illustrative units, not measured efficiency. The causal direction, the necessity of handling B, the meaning of the `Established` states, and the feedback protocol require independent incident evidence.

## 2. 案例如何引出两个挑战和三个模块

- **C1 Local Ambiguity / 局部关系歧义。** A→B、B→C 和 B→D 只是竞争关系假设；时间先后、状态标签或排名不能单独证明方向。局部证据可能支持、冲突或缺失，缺失不能当作 No Direct。
- **C2 Global Consistency / 全局一致性。** 局部支持需要在共同锚点条件下组合；不能产生环、脱离锚点或无证据的补边，但图合法也不等于关系正确。
- **M1 事故证据图构建。** 汇总异常上下文、告警、日志、时间戳和拓扑，附证据引用与缺口。
- **M2 局部传播关系建模。** 在原始拓扑允许的设备对上表示正向、反向、No Direct、未知和冲突。
- **M3 锚点引导的全局传播图重建。** 估计/接收候选锚点，在其条件下选择关系并组装解释 DAG。

这三个模块是论文方案组织，不等于三段新代码。现有实现仍按 Stage 1（PC-STGR 根候选）和 Stage 2（P0 局部支持与条件 DAG）描述；Stage 1 支持 M3 的锚点候选功能，M1 是分散的证据整理职责。单设备根、原始 `task_topo` 邻接和 unknown 掩码约束保持不变。

## 3. 旧 DEMO_001：历史可复核示例，不与 PPT 案例混用

旧示例仍使用仓库标注工具内的 [DEMO_001 观测](../../../pingmesh-propagation-labeler/examples/demo_cases/DEMO_001/nodes.json)及其[触发信息](../../../pingmesh-propagation-labeler/examples/demo_cases/DEMO_001/info.json)。它包含 H1–H2 端到端丢包、C 的接口 down、S 的 BGP 会话回退、C 的 peer 状态由 Established 变为 Idle，以及 L1/L2 没有事件记录。它只用于说明“端点异常之后还需要核查设备关系”，不是 PPT 的 A/B/C/D 案例。

只使用 `info.json` 与 `nodes.json` 中的观测。`demo_predictions.json` 是旧原型的人工构造输出，含观测文件没有的路由撤回事件和示意分数，不能作为引入证据、标签或模型结果。物理边 C–S、S–L1、S–L2、L1–H1、L2–H2 也不能因为存在就被写成传播边。

| 可复核观测 | 可用写法 | 不可推出 |
|---|---|---|
| H1–H2 Pingmesh 丢包 | 端到端异常触发诊断 | 具体 Web 请求超时或逐跳路径 |
| C 接口 down、S BGP 回退 | 形成 C/S 关系核查线索 | C 是唯一物理根因 |
| C 的 peer 状态 Established→Idle | 记录状态转换 | 日志顺序就是传播方向 |
| L1/L2 无记录 | 证据缺口/未知 | 设备正常、异常未经过或存在路由撤回 |

## 4. 可直接替换的引入正文

考虑一次 Web 服务依赖的数据中心网络出现端到端异常后的诊断场景。Pingmesh 可以作为异常探测入口，但探测到丢包并不会自动告诉工程师哪些设备异常、哪些异常之间存在直接影响，或哪些恢复动作仍然必要。PPT 的 A/B/C/D 示意把这个缺口表达为一条可能的 A→B→{C,D} 关系：即使 A 已经排在可疑设备列表第一位，关系解释仍可能影响先检查谁、哪些下游状态可以等待反馈，以及何时停止。这里的 4→2 只是待验证的动作假设，不是效率结果。

本文因此研究：给定一次 Pingmesh 异常、原始物理拓扑以及故障窗口内可用的设备告警和日志，在单设备起点范围内恢复 incident-specific 的设备级传播解释 DAG。系统需要保留局部关系的方向歧义和证据缺口，并在候选锚点条件下组织整体一致的解释，同时提供证据引用、替代关系和未决部分。该输出不是真实 ECMP 路径、完整因果模型或自动修复策略；图质量和恢复决策价值需要分别通过受控实验与真实反馈验证。

## 5. 验证所需的最低材料

若要把 PPT 的动作价值写成实证，需要为同一事故记录：初始排名、可见观测、候选传播关系、每个检查/修复动作的定义、权限和成本、A 修复后的设备状态、B 仍需处理的依据、C/D 的前后状态转换、自动恢复延迟、停止规则以及基线获得的相同反馈。评估时必须区分检查、修复、确认正常和自动恢复；不能强制排名基线逐台操作，也不能用算法自己的图决定模拟器的恢复结果。

后续真实案例到位前，本文只保留 PPT 作为方案动机和 `DEMO_001` 作为合成观测示例，不声称 Web 业务损失、MTTR 或人工排障收益。
