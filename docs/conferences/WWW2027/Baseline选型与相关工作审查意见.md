# Baseline 选型与相关工作审查意见

日期：2026-09-09。审查对象：[Related_Work与Baseline选型](./Related_Work与Baseline选型.md)、[Introduction中文初稿](./Introduction_引入与以往工作_中文初稿.md)。配套交付：[Baseline实现任务书](./Baseline实现任务书_供独立智能体执行.md)。本次核对论文、公开实现及本仓库代码，没有修改上述两份原稿，没有运行新训练或报告性能结论。

## 1. 总体判断

**选型方向合理，但当前名单尚不能直接冻结为最终主表；相关工作正文总体顺畅，但与选型表覆盖不一致，对最接近传播方法的差异论证还不充分。**

值得保留的部分：把根因定位、固定根传播图和自主完整流程分开；以 NetEventCause 作为最接近的事件传播对照、BiAn 作为语义定位对照；不把 TraceRCA 的合成交易实现冒充原法；缺少特定遥测时不强行复现 Hawkeye 等方法；把原生算法和本项目适配明确区分。

需要改变的是“哪些候选已具备公平可比的实验定义”，而不是简单增加 baseline 数量。尤其是 NetRCA 的任务不匹配，NetEventCause 的公开代码并不完整，REASON/CORAL 的因果图也不能仅靠设备投影就被视为一次故障的传播图。

第一轮建议准备三项核心方法与两项有条件的通用图方法，同时审计 NetCause。全部条件通过时约有五至六项有明确分工的外部对照；不要求把所有候选强行凑入实验。如果时间序列条件不成立，不能为填表而用大量补零制造图方法输入。

这不是“足够数量即可证明有效”。传播主张仍需要可靠的外部近邻、固定根下的图比较，以及对本文局部支持/结构组织的消融共同支持。普通因果发现方法只能补充方法谱系覆盖，不能代替 NetEventCause 或 NetCause 等强近邻。

## 3. 会影响选型的实质问题

### 3.1 NetRCA 不适合作为当前任意设备排名基线

原稿 §1.4、主表及 R6 把 NetRCA 概括成可以迁移到设备 Root 的网络定位方法，概括过宽。原论文处理无线网络 KPI、固定根因类别及其组合；方向特征涉及波束/位置，不是设备间传播方向。重新构建设备特征、训练任意设备排序器，会改变任务与核心机制。建议撤出，保留相关工作时归入特征工程/领域知识诊断，不放进“LLM 辅助”共同机制中。[NetRCA 原文 §2–3](https://arxiv.org/pdf/2202.11269)

### 3.2 NetEventCause 选得对，但“接入作者代码”的工作量被低估

公开 README 明示部分代码被替换。本地作者目录的 toy 脚本默认使用 ERPP，训练/归因入口引用的 ODE-RNN 等模块在对应目录缺失。公开归因代码还包含针对五种类型写死的关系限制。直接运行这些代码，不能据此宣称实现了论文中的 NEC。[作者仓库说明](https://github.com/yuanzhaolin/NetEventCause)、[公开归因代码](https://raw.githubusercontent.com/yuanzhaolin/NetEventCause/main/detect/attribution_rca.py)

还有一项监督条件需要补充：论文的根告警先验估计使用少量根告警标注；“知道根设备”不能推出“该设备所有告警均为根告警”。应列明先验来自训练期事件标注还是工程校准。使用校准适配可以实施，但须更名并披露，不把它写成原版先验估计。[本地论文 §IV-B](../../papers/NetEventCause_%20Event-Driven%20Root%20Cause%20Analysis%20for%20Large%20Network%20System%20Without%20Topology.txt)

最适合的安排是：按论文模块核对、补齐核心模型和归因，再进行设备适配；名称明确为论文机制复现。旧 `NECAnalyzer.py` 的 Hawkes 实现不能承担这一角色。具体任务已写入实现任务书 A1。

### 3.3 REASON/CORAL 的图列承诺过早

REASON 面向有层次关系的实体指标与 KPI，通过因果网络等机制进行根因排名；CORAL 面向连续监控流，学习随状态变化的因果关系并进行在线诊断。其原生图有诊断价值，但图边不自动表示“在这一事故中实际激活的直接设备传播”。[REASON 作者正式论文](https://nijingchao.github.io/paper/kdd23_reason.pdf)、[CORAL 作者论文](https://arxiv.org/abs/2305.10638)

**设备投影只解决节点粒度，不解决当前事故的关系选择。** 例如某指标之间长期存在依赖，并不意味着本次故障确实沿该关系传播。即使给定真实根，也不能据此知道所有激活边。因此，原稿 G3/G4 只要导出邻接矩阵就评价 Oracle/Full 的定义不充分。

建议先审计它们的 Root 迁移。若要加图实验，应独立声明“原生因果支持图 + 本项目事故适配”的规则和新增假设，并与原生事件传播方法分组解释；不能把这一步只叫粒度映射。CORAL 的图是状态相关的，也不应反向贬为只能输出静态图。

### 3.4 PCMCI+/DYNOTEARS/TCDF 可以做补充，但不能按原稿直接落地

PCMCI+ 可能输出未定向同期关系；DYNOTEARS 区分同期和滞后边，时间展开图无环不保证设备折叠后无环；TCDF 同样需要保留时延含义。这些关系都不能不加说明地变成一个根条件设备 DAG。[PCMCI+ 论文](https://proceedings.mlr.press/v124/runge20a.html)、[Tigramite 输出说明](https://github.com/jakobrunge/tigramite)、[DYNOTEARS 论文](https://arxiv.org/abs/2002.00498)、[TCDF 作者实现](https://github.com/M-Nauta/TCDF)

原稿 G5 写“Oracle 根不改变预测边”，而 NEC 适配却用根删入边、去环并保留可达子图，二者得到的先验待遇不同。建议统一保存原生图，并在单独的公共适配阶段使用根；所有方法采用同一设备投影与结构规则，名称附 `+ device adapter`。未定向关系必须保留为未决，不能按根距离强制定向。

分箱后的事件计数不等于原论文使用的连续指标；稀疏、常量、短窗口、缺失和采集不完整都可能影响可识别性。先在实际训练数据上做 A4 审计，再冻结哪些方法进入实验。DYNOTEARS 已有作者团队公开实现，可以优先复用而非一律从零复现。[CausalNex 实现](https://github.com/mckinsey/causalnex/blob/develop/causalnex/structure/dynotears.py)

这里对所有因果图方法采用同一标准：即使在当前窗口估计图，也不能自动解释为已识别全部激活传播边。PCMCI+/DYNOTEARS 优先，是因为有明确公开入口、可定义逐例输入且不额外要求层次实体/KPI 流；不是因为它们不存在语义迁移问题。若 REASON/CORAL 同样满足输入并完成相同程度的适配定义，也可以另列图迁移实验。

### 3.5 NetCause 是应认真对待的近邻，文献状态也可更新

它已经把异构拓扑、事件状态与影响上下文用于传播动态学习和反事实根排序；不能把“融合拓扑与时间”当作本文独有贡献。它不原生输出本文要求的逐边设备传播图，因此 Root 入选、图列不支持的判断合理。[NetCause 作者正文](https://arxiv.org/html/2606.13543v1)

原稿只称“2026 预印本”并不完全反映作者声明：当前 PDF 首页标注已被 ICCCN 2026 接收。可写“ICCCN 2026，本文引用作者预印本”；最终出版 DOI 本次未确认。[作者 PDF 首页](https://arxiv.org/pdf/2606.13543)

### 3.6 SkyNet 和 BiAn 的适配命名基本合理，规则需收紧

SkyNet §7.1 确有告警投票，但“所有一跳邻居各得单位票”是本项目的设备化选择，不是已完整公布的算法。应先固定告警/链路归属映射，不能按方法名推断每条日志该给谁投票。[SkyNet §7.1](https://ennanzhai.github.io/pub/sigcomm25-skynet.pdf)

BiAn 使用设备分析、拓扑、全局时间线及联合推理，且有重复排名聚合和知识演化机制。当前 Pipeline1 可以保留为简化版本；主适配应补齐现有输入支持的三条流程，统一候选预算，并披露历史知识/SOP 缺项。[BiAn §4](https://ennanzhai.github.io/pub/sigcomm25-bian.pdf)

### 3.7 “当前有哪些输入”还不能只沿用文稿概括

本机两个原始导出中有 `task_trace` 字段（一例非空、一例为空），也有 `cross`、`probability_calibration` 及 `groud_truth` 等观测、派生分数和标签混合字段；样例的 `log_list` 只有汇总计数。故应坚持“不默认有精确路径”，但不能扩写成“数据里完全没有任何路径信息”；也不能把已有派生诊断分数直接当普通探测事实。实现任务书列出了字段白名单审计要求。

这项发现不改变 TraceRCA 需要微服务调用 trace、NetBouncer 需要特定路径测量结果的比较边界；它说明排除与适配理由应来自字段及观测语义，而非仅看文件名或是否存在某个键。原始导出含真值也不等于已经发生训练泄漏，必须检查实际推理调用链。

## 4. 两份文字是否匹配、逻辑是否充分

### 4.1 对引入的判断：主线顺，但有重复和边界未进入正文

前四段完成了“服务依赖网络 → 排名不够 → 局部观测不能直接成图 → 定义任务”的推进，核心逻辑成立，不需要整体推翻。

建议小幅压缩第二段与第四段反复出现的“方向、路径、分支、可检查解释”；第二段集中说明为什么需要图，第四段只给任务定义。单根、设备直接边对应物理邻接、静态 DAG 的范围现在主要存在于配套大纲，最好在任务定义处明确一句，避免读者理解成一般网络故障因果恢复。

可在引入末段补充：

> 本文限定于单设备根因可解释的故障实例，并以原始物理相邻设备之间的直接影响关系构成静态有向无环传播解释；其边表示由当前观测支持、可供核查的传播假设，而非精确逐包路径或对完整网络因果机制的识别。

这是一项建模边界，需要在数据选择与标注规则中落实。控制面跨多跳影响、真实反馈回路和多根事故可能超出此契约；应事先报告覆盖范围，不能把模型不擅长的实例事后剔除。

### 4.2 对以往工作的判断：概括没有明显断裂，但证据跳跃较大

正文第 16 行实际只有一段，明确举例只有 BiAn 和 NetEventCause；第 33 行却称扩展正文覆盖 11 项工作，目录 README 和大纲也仍描述为四类扩展正文。这是内容状态不同步。参考文献列出 11 项，不等于正文已讨论 11 项。

不要求 Introduction 罗列所有实验方法。合理安排是：引言覆盖关键方法族与最近邻；独立 Related Work 解释其他候选和输入边界；Baseline 小节说明哪些方法用于哪个任务。若保留一段压缩版，就应修改“已按四类展开”的元说明，而不是机械地塞满方法名。

最需要补强的三处论证：

1. **“排名不等于图”是任务动机，不是技术创新的完整论证。** 需要继续回答已有事件图为何不能通过简单投影解决问题，以及本文结构组织相比共同适配器增加了什么。
2. **“事件图不直接等于设备图”说得对，但不足以排除简单映射。** 应说明同设备多次事件折叠会产生冲突/环、事件间影响可能跨越未观测设备、部分异常与当前根无关；然后用 NetEventCause 原始投影、共同适配、本文方法的对照验证差异。不能预先写成这些问题在本数据上普遍发生。
3. **“部分方法依赖特殊输入”需对应到具体工作。** 调用 trace、可控路径测量、PFC provenance 和 SOP 是不同条件，不能笼统归为“完整信息”；缺少这些条件说明迁移受限，不说明原方法效果差。

“另一类工作开始回答异常如何传播”略带把已有研究描述为刚起步的倾向，可换成“另一类工作显式建模事件依赖或机制相关传播”。同时承认 Hawkeye 已有传播溯源、NetCause 已有事故传播动态，避免只对比弱化后的前人。

### 4.3 可直接替换第 2 节的正文建议

以下是建议稿，未覆盖写入原文。参考文献编号沿用原稿的 [1]–[11]；PCMCI+ 等新增引用可在独立 Related Work 中统一编号。

> 已有研究从测量、告警分析和跨设备推理等角度缩小网络故障范围。Pingmesh 提供持续的端到端异常观测，deTector 和 NetBouncer 进一步利用具有特定控制条件的路径测量定位内部故障；TraceRCA 则利用分布式调用 trace 排查可疑服务 [1–4]。COLA 和 SkyNet 将大量告警组织为关联事件与故障范围，BiAn 综合设备异常、拓扑和全局时间线生成可疑设备排名 [5,6,11]。这些能力为故障诊断提供了基础，但位置、告警分组或设备排序本身尚未确定一次故障中设备之间的直接影响关系。
>
> 与传播重构更接近的是事件依赖及传播建模工作。NetEventCause 学习连续时间事件模型，识别根告警并分析当前序列中告警实例之间的影响关系 [7]；Hawkeye 利用 PFC provenance 追踪 RDMA 性能异常的传播与来源 [9]。NetCause 则在已知异构拓扑上学习故障和操作状态的演化，通过反事实模拟对候选根因排序 [8]。这些方法已经涉及传播分析，因此本文的区别不能仅概括为使用拓扑与时间，或输出有向关系。
>
> 本文需要进一步处理事件关系到设备传播解释之间的差异。一个设备可以在不同阶段产生多个事件，事件图在折叠为设备图后可能出现双向关系或环；事件之间的影响也未必对应一条直接物理连接。与此同时，窗口内共现的异常未必都属于同一故障过程，缺失的设备事件又使简单投影难以说明哪些关系应被保留。因此，已有事件关系能提供传播支持，但仍需要在明确的设备粒度、物理邻接和单根条件下进行选择与组织。这些差异应由统一适配后的对照实验检验，而非由输入或输出名称预先推定。
>
> 基于这一问题，本文在 Pingmesh 异常触发后，利用实际可获得的端点上下文、设备告警、日志及原始物理拓扑，研究单设备根因条件下的故障传播图重构。本文将候选起点判断、局部方向支持与整体结构恢复衔接起来，并分别评价根因定位和传播图质量。精确路径、专用 PFC 遥测及完整运行知识不作为默认输入；恢复的图则作为可逐边核查的当前故障传播解释。

独立 Related Work 还应补一段通用因果发现：PCMCI+、DYNOTEARS、TCDF 提供时间关系发现能力，REASON/CORAL 将因果网络用于诊断；比较重点是它们的观测序列与原生图语义如何迁移到本任务，而不是宣称它们都不支持当前事故分析。NetRCA 如保留，仅用来说明特定领域特征与固定类别诊断，避免继续承诺设备 Root 实验。

此建议稿主要修补论证与覆盖；是否最终采用四段或压缩为两段，应由整个 Introduction 篇幅决定。

## 5. 必须在实现前修正的实验协议

| 原稿位置/问题 | 建议修正 | 不修正的后果 |
|---|---|---|
| §5 禁止用无标签测试事件拟合，表述过宽 | 区分跨案例参数训练、逐例无标签图发现、在线无标签更新；分别冻结输入截止时间与状态范围 | PCMCI+/TCDF/CORAL 被禁止执行原生推断步骤，或实际执行后被错误称为纯 OOF |
| §2.4/G5 与 §3 的 Oracle 根处理不同 | 原生图保存不变，公共适配阶段统一使用根；明确本文方法原生根条件解码的差异 | 不同方法获得不同结构先验，无法解释比较结果 |
| §2 主表用普通 Edge-F1 代表完整任务 | 同报根正确率、普通图分数及根正确条件下的联合分数 | 根错但共享大量下游边仍可取得高 F1，掩盖根错误 |
| `X` 同时被用于任务不支持和输入不成立 | 候选审计、能力不适用、输入覆盖、实现状态和运行失败分开 | 很容易在看到差结果后通过换标记删除方法/样本 |
| 把全部未知/possible 关系混在普通集合计分中 | 明确必需、允许、未决、负例及完整标注语义；版本化评测器 | 未决关系被错误计成 FP/FN，整图匹配失去明确含义 |
| “PC-STGR（ours）”承担三类结果 | Root 使用 PC-STGR；完整图行明确为“本文方法（PC-STGR + P0）”或统一正式系统名 | 阶段方法与系统方法名称混淆 |
| 独立启发式全部叫“消融” | Earliest/Alarm-count 叫轻量参照；移除本文模块的对照才是消融，可同在辅助实验章节 | 方法身份含糊；完全取消轻量参照又难以解释简单方法是否已经足够 |

具体接口、指标公式、适配顺序、每个方法的验收均见实现任务书。不建议让不同智能体各自开发一套数据划分和评分器。

## 6. 还缺哪些证据，才能说论证充分

1. **任务和标签可信度。** 传播标签来自何种专家证据，哪些边确定/允许/未知，是否有独立复核，标注是否看过本文输出。若真值主要由 P0 自动生成再确认，必须披露可能的同源偏差；不能直接把解码器偏好当成真实传播规律。
2. **普通观测的实际困难。** 统计无根设备告警、时间并列/延迟、低事件密度、混杂异常等现象；无法判定是否缺失时不要硬计成观测缺失率。论文案例证据和本数据统计分开。
3. **事件到设备适配的代价。** 原生 NetEventCause 投影中的冲突、非邻接、去环及不可达删边比例，以及适配前后图质量。设备折叠可能形成环是逻辑例子，比例大小必须由数据给出。
4. **整体结构的独立作用。** 固定同一根、同一局部边支持，对比局部选边、局部选边加共同适配、P0；单独分析根距离限制和图大小。结构合法率高不能替代边正确率高。
5. **可检查解释的实际价值。** 若只做边级评价，就写“提供可核查结构”；若声称减少排查成本或改善运维，再给专家核查、检查对象数或时间等证据。没有这类实验也可以发表方法结果，但不提前承诺运维收益。

现有本机数据目录不足以重验全量案例数、标注质量和时间序列覆盖；本次结论是有论文与代码证据的选型/实现审查，尚非全量数据可行性证明。下一步先做任务书 A0/A4，再由各智能体按同一契约实施。
