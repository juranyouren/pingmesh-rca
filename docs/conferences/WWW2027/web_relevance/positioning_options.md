## 0. 三个方案的共同起点（不因方案不同而改变）

以下问题定义**三个方案都保留**，区别只在论证链与服务对象：

- 单设备根；Top-K 表示**相互竞争的单根假设**，不是多根同时故障。
- 输出 = 选定起点 + 显式设备节点 + 有向传播边 + 证据引用 + 备选解释 + 未决关系。
- 每条输出的设备边**必须存在于原始 `task_topo`**；unknown 掩码，绝不转为负例；allowed 中性。
- 输出是**观测支持的依赖假设**，不是 ECMP 逐包路径，不是干预因果图，不是根因排名。
- 演示数据 `DEMO_001` 是**合成**案例；历史预测文件不是观测或真值。当前**没有**真实事故复盘、
  没有服务—端点依赖说明、没有工程师任务测量（见 [STATUS](../../../../.ai/STATUS.md) B01–B08）。

## 方案 A：Web 云网络的诊断基础设施（Infrastructure-first，对应方式 C）

### A.1 一句话定位

**面向支撑 Web 服务的共享云网络，把"从多端点异常恢复可核验的设备传播解释图"定义成一项
网络运维基础设施能力。**

英文 Web relevance 表述（2–3 句，待部署依赖证据到位后定稿）：

> Web services run on shared cloud networks, and a single network incident can surface as
> connectivity anomalies across many endpoint pairs. Diagnosing such an incident requires
> more than naming a suspect device: engineers must establish how the affected devices relate
> to one another. We study the reconstruction of an auditable, incident-specific device
> propagation graph from endpoint anomalies, raw topology, and partial device evidence.

**注意**：第一句目前**没有**部署证据（我们不知道这些端点承载哪些服务）。
按 [旧调研 §7.2](../WWW近三年网络相关论文检索与投稿契合分析.md) 的要求，
若无法验证，应把第一句降为一般背景并**立即明确数据边界**，不得改写成未测量的业务失败数量。

### A.3 中文开篇示例（约 260 字）

> 支撑 Web 服务的数据中心网络是一张被多个服务共享的连通底座。一次网络故障很少只影响一条
> 链路：Pingmesh 这类端到端测量会在同一故障窗口内报出多组端点对的异常，而设备侧的告警与
> 日志只覆盖其中一部分节点。工程师拿到的是一组**症状**，需要回答的是这些症状背后设备之间
> 的关系。现有工具能给出可疑设备的排序，却无法说明排在前面的设备之间如何相互影响、影响沿
> 哪条路径展开，也无法说明哪些关系其实没有证据。本文研究的就是这一层：在异常端点、原始
> 物理拓扑与不完整的设备告警/日志之下，恢复与本次事故对应的设备级有向传播解释图，
> 并逐边给出支持证据与未决关系。
>
> 【待补证】首句"支撑 Web 服务"需要部署依赖说明支持；当前无该材料，需补或降级为一般背景。

但要求补一份部署依赖说明（写作材料，非实验）。

## 方案 B：工程师可核验的根因解释（Auditability-first，对应方式 B）

### B.1 一句话定位

**把评价对象从"根因排名的准确率"改成"工程师能否逐边核验一个故障解释"，
以诊断决策质量而非模型分数建立 Web 相关性。**

英文 Web relevance 表述：

> When a web-facing service degrades, engineers must decide which devices to inspect and in
> what order. A ranked list of suspects does not tell them how the suspects relate, nor which
> relations are unsupported by evidence. We study how to produce an incident-specific device
> propagation graph whose edges are individually verifiable against raw topology and
> operational evidence, and we evaluate it as a diagnostic artifact rather than a ranking.

### B.2 Introduction 提纲（7 段）

| 段 | 目的 | 关键论点 | 承接 | 可引 | 引用类型 |
|---|---|---|---|---|---|
| P1 | Web 服务可靠性依赖故障恢复 | 服务中断的成本由**定位与恢复时间**决定，不由模型分数决定 | — | `www24-gamma` Intro P1–P2（"customer experience and revenue"） | 借鉴动机 |
| P2 | 工程师实际要做的判断 | 收到异常后要划定检查范围、排出顺序、记录依据 | P1 | `comp25-flow-of-action`（SOP 支撑**已有流程**；仅 Industry 引用，不得当先例） | 借鉴动机 |
| P3 | 现有产物不够用 | 排名只给顺序，不给设备间关系；图不给出处就是不可核验的 | P2 | `www24-mulan` §1（排名输出）；`www24-gamma` §3.2.1（调用图是**输入**） | 借鉴动机 + 区分技术 |
| P4 | 缺口说得窄 | 缺的不是"更准的排名"，而是**逐边可核验的解释产物**与**未决关系的显式表达** | P3 | `www26-starlink-cd` §5 的缺口写法（把缺口定义成某一测量维度缺失） | 借鉴动机（写法） |

### B.3 中文开篇示例（约 290 字）

> 当面向 Web 的服务出现质量下降时，工程师要做的第一件事不是断定某台设备是根因，而是决定
> 先查什么、按什么顺序查、查到的结果怎么记。这个决定的质量直接决定恢复要花多久。现有工具
> 大多给出一个可疑设备的排序，但排序回答不了"这些设备之间是什么关系"，也回答不了"哪些关系
> 根本没有证据"。工程师因此需要另一种产物：一张与本次事故对应的设备级有向影响图，图上的
> 每一条边都能落回原始物理拓扑，并携带支持它的告警或日志，同时把无法判定的关系显式标为未决。
> 本文研究这张图的恢复方法，并把评价对象从模型分数改为**工程师能否逐边核验这张图**。
>
> 【待补证】"恢复要花多久"目前**没有**任何测量；须补工程师任务数据，否则删去该句。

### B.4 四要素引出

P3 的"可疑设备排序"给出**单设备根与竞争起点**；P4 的"逐边可核验"引出**局部方向支持**；
P6 的"图上每条边落回拓扑"给出**传播解释 DAG**；P7 的**工程师任务指标**是本方案独有。
**要求增加数据**：工程师任务测量（检查集合、接受率、时间）。

### B.5 支撑论文与页段

- **借鉴动机**：`www24-gamma` Intro P1–P2；`www24-wise-start` §4（生产部署评测）；
  `comp25-flow-of-action` Intro（**Industry/Companion，须明示轨道**）。
- **借鉴技术**：本项目 `graph-eval-v2` 协议（[图评价协议](../故障传播图指标调研与最终评价方案.md)）。
- **区分技术**：`www24-mulan`（排名评价 vs 我们的边级评价）。

### B.6 证据表

| 类别 | 内容 | 最小补证任务 | 可检验假设 |
|---|---|---|---|
| **已有证据** | P0 解码器、OOF 预测、`graph-eval-v2` 协议（已规定未完全实现）、合成案例 | — | — |

### B.7 审稿质疑

1. **"这本质上还是网络运维，为什么是 Web 论文？"**
   可回答：评价对象是面向 Web 服务的**诊断决策质量**；若任务实验成立，它回答的是
   "Web 基础设施故障如何被有效诊断"这一 Web 科学问题，而非通用网络算法问题。
   **无法回答时收窄**：若无法做任务实验，本方案退化为方案 A。

2. **"任务实验的被试数量与代表性？"**
   可回答：需预先注册最小样本量与纳入标准。**若无法达到**，应把任务实验降级为
   illustrative 案例并明确标注，**不得**声称效率或 MTTR 收益。

3. **"你们的边级指标口径与既有 RCA 工作不可比。"**
   可回答：这正是主张的一部分——排名指标与边级指标衡量不同对象；须给出同一预测在
   两套指标下的结果，说明差异来源。

### B.8 投入判断

**需新增实验 + 需补场景材料**。人因任务实验是新增工作量最大的一项；
若无法获得工程师被试，本方案不可行，应回退到方案 A 或 C。

## 方案 C：证据不完整下的图结构不确定性（Science-first，对应方式 C+科学问题驱动）

### C.1 一句话定位

**把科学问题定位成"不完整证据下图结构的可恢复性"，Web 相关性由
"规模化 Web 部署使证据不完整成为常态"建立。**

英文 Web relevance 表述：

> Web-scale infrastructure makes complete, synchronized telemetry the exception rather than
> the rule: which device originates an incident, and which direction influence propagated,
> are both under-determined by the available evidence. We study what graph structures remain
> recoverable under that under-determination, and how to expose the residual ambiguity rather
> than resolve it arbitrarily.

### C.2 Introduction 提纲（6 段）

| 段 | 目的 | 关键论点 | 承接 | 可引 | 引用类型 |
|---|---|---|---|---|---|
| P1 | 提出一般现象 | Web 规模部署下，遥测不完整、不同步、有歧义是常态而非例外 | — | `www26-starlink-cd` P6（跨层复合错配的具象化写法） | 借鉴动机（写法） |
| P2 | 具体化 | 一次 incident 中：起点不确定；设备对之间的方向证据不足；局部成立的关系未必能组成一致图 | P1 | 本仓库 C1/C2/C3 | — |
| P3 | 指出现有做法的问题 | 把未观测关系当作负例、把起点当作已知、把局部关系直接拼接，都会产生**看似确定但无依据**的输出 | P2 | `www24-gamma` §3.2.1（调用图来自 trace 历史，是输入假设） | 借鉴动机 + 区分技术 |

### C.3 中文开篇示例（约 250 字）

> 在支撑 Web 服务的规模化云网络中，完整且同步的遥测是例外而不是常态。一次网络异常的
> 窗口内，设备告警可能只覆盖部分节点，时间戳不同步，日志的采集范围本身就带有盲区。
> 在这种条件下，两个问题同时变得不确定：故障从哪台设备开始，以及影响沿哪个方向传播。
> 已有做法通常默认其中一个问题已经解决——要么假定起点已知，要么把未观测到的设备对
> 直接当作无关联。本文研究的是另一个问题：**在证据本身不完整时，哪些图结构仍然可以被
> 有依据地恢复，哪些不能。** 我们把无法判定的关系显式标为未决，而不是用默认值填补，
> 并给出在固定起点与不确定起点两种条件下的重建结果与误差。
>
> 【待补证】首句需要至少一条我们自己的观测依据（如采集覆盖率统计）；当前无，需补或改为引用文献。

## 方案对比与推荐

| 维度 | A 基础设施定位 | B 可核验解释 | C 结构不确定性 |
|---|---|---|---|

| 是否需改研究范围 | 否 | 否 | 否 |

**首选：方案 A**。理由：它是**唯一在现有证据条件下不虚构任何事实即可成文**的方案，
且轨道归属有官方文本明文支持；补证成本最低（一份脱敏依赖说明）。
其弱点（关联仅到基础设施层）是真实的，应当在论文中**如实承认**而不是用措辞掩盖。

**备选：方案 C**。理由：与现有资产匹配度最高，且 C1/C2/C3 是可证伪的科学主张，
科学贡献最扎实。若用户接受"Web relevance 较弱、可能被质疑"的风险，或若补证材料长期不到位，
C 是更稳的科学选择。**A 与 C 可以合并**：A 提供定位，C 提供科学问题。

**条件性推荐：方案 B**。只有在**能获得 ≥1 个真实 incident 与工程师任务数据**时才推荐。
否则 B.3 开篇中的"恢复要花多久"与整个第 7 段的评价主张都无法成立。

**暂不推荐：面向 Agentic Systems 的 LLM 证据接口。**
即"把输出 DAG 包装成 agent/LLM 可消费的证据结构"以贴合轨道名。
理由：① 项目约束明确**实验不得调用外部 LLM API**；② 为贴题临时加入 agent
并不能补上服务关联证据（[旧调研 §2](../WWW近三年网络相关论文检索与投稿契合分析.md) 已论证）；
③ 这是"仅替换术语"而非"实质差异"，不满足任务书对方案差异性的要求。
