# Analysis card template

每篇论文一个 `papers/<paper_id>/analysis.md`，结构必须一致。
篇幅 800–1500 中文字（复杂论文可适度增加）。**质量优先于篇幅。**

## 证据标注规则（必须遵守）

在每一处判断后标注来源类型，三者不得混淆：

- `【作者陈述】`——论文正文明确写出的说法，需给页／节／段位置。
- `【实验支持】`——由后文实验、测量或部署数据支撑，需给节／表／图位置。
- `【本次推断】`——本次分析的推论，论文并未这样说。

**禁止**：把摘要当引言；把引言中的动机陈述写成已被验证的收益；
对未读到的部分补写内容；用模型生成文字填补缺字而不标记。

## 卡片结构

```markdown
# <paper_id> — <正式题名>

| 字段 | 值 |
| --- | --- |
| 年份 / 轨道 | |
| 正式题名 | |
| DOI | |
| 原始 PDF | <文件名>（来源：<URL>；版本：<arXiv vN / author copy>） |
| 抽取文本 | tmp/www-web-relevance/txt/<paper_id>.txt |
| Introduction 定位 | <paper_id>.intro.md，PDF 第 x–y 页，P1–Pn |
| 深读状态 | 已深读 / 部分深读（说明缺什么） |

## 1. 问题定义
研究对象、输入、输出、使用者／受益者。网络问题为何值得研究？
（注意区分作者声称的使用者与论文实际能支持的使用者。）

## 2. Web 关联
具体涉及哪个 Web 系统／服务／基础设施需求？关联出现在引言哪一页哪一段？
是"标题级限定词""引言首段背景数据"还是"仅领域命名（microservice systems）"？
去掉 Web 术语后，论文的技术主张是否仍然成立？

## 3. 段落作用（按 P1、P2……）
逐段说明该段在论证中的实际功能（背景→重要性→现有工作→缺口→挑战→洞察→方法→贡献），
不要强套模板；若某段承担多种功能或顺序不同，照实写。

## 4. 现有工作与缺口
作者具体批评哪些能力不足？该缺口如何推出自己的方法？
（写作者实际批评的内容，不要泛化成"已有工作不够好"。）

## 5. 核心洞察与贡献
区分：任务定义贡献 / 方法贡献 / 系统实现贡献 / 工程规模贡献 / 评价贡献。
指出哪一项是论文真正的立身之本。

## 6. 证据强度
引言里出现的收益或规模数字，由后文哪些数据／实验／指标支撑？给出节／页／表位置。
哪些只是动机陈述或推断？有没有"只测了 X 却声称 Y"的情况？

## 7. 与本项目（RPG-Recon）的关系
- 可借鉴的**论证步骤**（如何把网络问题连到 Web）
- **不能迁移的前提**（数据、部署、评价条件）
- 与我们已有机制的**潜在重合**（若重合，说明我们的差异在哪）

## 8. Reviewer 视角
- 若去掉 Web 术语，论证是否仍成立？
- 最可能被质疑的关联或贡献缺口是什么？
- 该论文有哪些做法值得我们避免？

## 9. 原文定位索引
列出引用到的关键位置：节号 / 页 / 表 / 图，便于复核。
```

## 常见错误（避免）

1. 把 Abstract 当作 Introduction 分析。
2. 只读 Introduction 就断言全文已验证服务收益——必须定向查看任务定义段、系统背景段、实验段。
3. 用"已有工作不足""结合了拓扑与时间"这类概括代替具体比较。
4. 把作者的未来工作或 motivation 写成已实现能力。
5. 编造页码。页码以 `<<<PDFPAGE n>>>` 标记为准；arXiv 版本页码 ≠ ACM 正式版页码，须注明版本。
