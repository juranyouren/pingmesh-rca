# 相关工作细化与 Baseline 选型

日期：2026-09-09。状态：完成文献分类、基线选择与代码可用性审计；本轮不运行新实验，不将现有不统一口径的结果填入主表。与[扩展中文正文](./Introduction_引入与以往工作_中文初稿.md)、[中文大纲](./Introduction_提纲_讨论稿.md)及[英文大纲](./Introduction_Outline_EN.md)配套。

研究对象：Pingmesh 异常触发后，在单设备根因假设下重构本次故障的设备间影响关系。输入为端点异常上下文、原始设备拓扑、告警与日志。不能默认具有精确探测路径、正常/异常调用 trace、PFC provenance、SOP 或完整历史诊断工单。

## 1. 文献按四类组织

分类以主要诊断依据及输出为主，不宣称各类技术互斥；例如 COLA 使用 LLM，但它的主要任务仍是告警聚合。相关工作覆盖面应比实验基线广；输入条件不同是讨论迁移问题的依据，不是宣称某方法效果差的依据。

| 类别 | 代表工作 | 共同关注的问题 | 与本文的比较重点 |
|---|---|---|---|
| 测量与路径约束定位 | Pingmesh、deTector、NetBouncer、TraceRCA | 从端到端/调用路径观测定位内部可疑组件 | 主动路径测量和调用 trace 的可获得性；位置、链路健康与设备传播方向的区别 |
| 告警聚合与故障范围分析 | COLA、SkyNet | 将大量告警组织为事件集合、故障范围和优先级 | 告警同因/关联及空间层次不自动给出直接传播方向 |
| 事件依赖与传播建模 | NetEventCause、NetCause、Hawkeye | 恢复告警影响、学习传播动态或追踪机制相关溯源 | 事件/设备/流端口粒度；不完整事件与专门遥测条件；根因排序和显式图恢复目标 |
| 知识及 LLM 辅助诊断 | RCACopilot、BiAn | 利用诊断信息与推理输出根因及解释 | 原方法的知识和观测条件；类别/排名/文本与可逐边评价的设备图之间的区别 |

### 1.1 测量与路径约束定位

| 工作 | 原始输入与机制 | 原始输出 | 本文定位与 baseline 决定 |
|---|---|---|---|

| [NetBouncer，NSDI 2019](https://www.usenix.org/system/files/nsdi19-tan.pdf) | 可控 packet bouncing 与逐路径收发计数，推断设备和链路状态 | 设备/链路故障及链路成功概率 | 如将来有真实逐路径测量，可作增强输入条件下的定位对照；当前不入主表 |
| [TraceRCA，IWQoS 2021](https://github.com/NetManAIOps/TraceRCA) | 正常/异常分布式调用 trace，异常检测、可疑服务集合挖掘和服务排序 | 根因微服务排名 | 路径覆盖归因的跨领域参考；现有设备告警和 cross 计数不等于 trace 集合，当前适配不列为原版 TraceRCA |

这些工作可归纳为“用路径观测约束内部故障位置”。不要写成“所有方法都要求主动探测”：TraceRCA 使用调用 trace，Pingmesh 与另外两项的具体测量条件也不同。

|---|---|---|---|

SkyNet Section 7.3 的案例说明，设备硬件错误日志可能晚于 BGP 断链、丢包和不可达告警出现，可支持 C1/C2 中“最早告警不一定对应根因”。这是该论文的案例证据，不是我们数据集已完成的统计观察。其 Section 7.1 已有设备图；区别在于图边主要表示已有连接，而本文推断故障实例的直接影响方向。

## 2. 主对比表设计与 baseline 选择原则

本轮主表按三个相互区分的任务打标：

1. **根因定位（Root）。** 不提供传播图，只评价设备根因候选排序：Top-1/3/5、MRR 和候选集召回率。
2. **Oracle 传播图重构（Oracle-Graph）。** 由评测包装层传入真实根设备，方法只负责重构该根对应的传播图；不把根因排序误计入图重构能力。
3. **完整传播图重构（Full-Graph）。** 不提供真实根，方法自行完成根因定位和传播图重构；根错或图错均计入端到端结果。

主表中的 `X` 有严格含义：该 baseline 的原始输出或允许的透明迁移无法定义相应任务，因此不报告该列数值；`X` 不是 0 分，也不是“尚未跑完”。已选中但尚未完成实现/实验的项目标为“待测”，不得用 `X` 掩盖未完成工作。只有原方法确实输出对应对象，或论文思路可以在不新增另一套推断器的情况下透明迁移时，才把该列列为可测。

对于 `Root baseline + P0` 的组合，只能另列为“共享本文传播解码器的全流程敏感性分析”，不能回填到上表的 Full-Graph 单元格，也不能把组合结果归因于该外部 baseline 自身的传播图能力。

### 2.2 baseline 选择顺序

按以下优先级冻结候选，不再为了填满三列而新增自建方法：

1. **优先使用已有论文和公开实现。** 首选 NetEventCause；随后审计 REASON、CORAL 以及 PCMCI+/TCDF 的图输出和输入条件；有代码则核对后接入，没有代码则按论文机制复现，并固定输入、训练折和设备映射。
2. **没有开源实现时按论文思路复现。** BiAn、NetCause、NetRCA 等允许做场景迁移，但必须列出原始输入、当前缺失字段、保留模块和删减模块；不能把适配版命名为完整原方法。
3. **场景不一致时做透明迁移。** 迁移只改变输入字段映射或输出粒度，不额外加入本文专用传播解码器。不能输出有向图的 baseline，在 Oracle-Graph/Full-Graph 对应单元填 `X`；Graph-only 方法即使能输出图，也不自动获得 Root 或 Full-Graph 能力。
4. **不再设置自建 baseline。** 如确有必要分析物理先验或解码器作用，只在消融章节报告，不进入 baseline 主表，也不与外部工作并列。
5. **特殊遥测方法暂不强行纳入主表。** Hawkeye 依赖 PFC/provenance 等当前场景没有的专门观测；除非建立明确的增强输入条件实验，否则保留为相关工作或扩展实验，不用伪造字段填结果。

“入选”表示计划实现并公平评价，不表示当前仓库已经具备完整实现或已经得到可报告分数。候选清单、输入适配、是否可测以及 `X` 标记必须在评测前冻结，不得根据跑出的结果反向删除 baseline。

| R3：BiAn-adapt（local model） | 检验网络场景中的语义与跨设备推理 | 现有证据可支持的设备分析、拓扑/全局时间线和联合排名应保留；模型、提示、输入缺项和历史知识限制均披露。不把仅 Pipeline1 称为完整 BiAn | 现有 Pipeline1 可作简化对照；主对照需补齐可支持的核心机制并核验原文 |
| R4：REASON-adapt | 检验层次化因果图与传播式根因排名 | 将设备/事件告警聚合成实体时间序列；映射层次实体关系；保存 learned causal graph，并在设备粒度投影后评价 | 新增候选；先审计时间序列构造、层次关系和图粒度 |
| R5：CORAL-adapt | 检验增量因果图和在线传播式定位 | 按 incident 时间顺序更新状态相关图；不得使用测试 incident 标签或未来窗口；若无连续实体时间序列则相应任务填 `X` | 新增候选；需先核对在线设定与当前离线评测协议的兼容性 |
| R6：NetRCA-adapt | 检验已有网络故障定位方法的根因排名 | 按论文特征定义审计当前告警、方向、归因和交互字段；只保留可由输入支持的特征 | 新增候选；仅进入 Root，不进入传播图任务 |
| Our Stage 1：PC-STGR | 本文候选根阶段 | 同一候选设备、事故划分与评测规则 | 按最终主配置报告 |

根因指标：Top-1/3/5、MRR、Top-K candidate recall。没有排出的设备视为未命中；若预筛选只保留部分设备，先报告候选召回，不能只在保留真根的子集计分。BiAn 不能直接沿用现有“按告警量截取 6 台”的默认范围与其他方法全设备排名比较。

NetCause-adapt 的追加价值：它与 PC-STGR 都利用事件子图、时空状态及拓扑，能提供比单纯中心性更强的学习式参照。首先核对原文的故障/操作状态与本数据字段是否对应；确实缺少操作或层级关系时，公开输入受限的适配，不伪造原系统观测。没有实现与实验前保留为待完成的强对照，不声称已覆盖所有强近邻。

### 2.4 固定根因的传播图表

| 编号 / 名称 | 构造规则 | 要检验的问题 | 方法性质 |
|---|---|---|---|
| G2：NetEventCause-Device | 将原模型告警实例传播边映射到设备对；保留原始输出诊断，并按第 3 节的固定规则形成可比较设备图 | 外部事件传播模型与设备传播重构的差异 | 外部模型＋明确披露的设备适配 |
| G3：REASON-adapt | 将论文学习到的层次因果网络投影到设备粒度；在 Oracle-root 下固定根并评估其图，在 Full-Graph 下使用其自身根排名 | 外部层次因果图能否恢复本文设备传播关系？ | 外部模型＋透明粒度适配；若只能输出稳定根排序，则 Oracle/Full 图列填 `X` |
| G4：CORAL-adapt | 将状态相关因果图投影到设备粒度；按原在线更新顺序处理当前事件窗口 | 增量因果图是否提供可评价的传播结构？ | 外部模型＋场景迁移；缺少有效时间序列时填 `X` |
| G5：PCMCI+-Graph | 在同一设备/事件时间序列上发现滞后与同期关系，映射为设备有向图；Oracle-root 只用于评价根相关子图，不用于改变预测边 | 经典条件独立因果发现能恢复多少传播边？ | Graph-only 外部方法；不输出根因排名，Root/Full-Graph 为 `X` |
| G6：DYNOTEARS-Graph | 在同一设备/事件时间序列上学习动态结构和滞后边，映射为设备有向图 | 连续优化结构学习能否恢复传播边？ | Graph-only 外部方法；不输出根因排名，Root/Full-Graph 为 `X` |
| G7：TCDF-Graph | 用公开 TCDF 发现带时延的时间因果图，再按输入归属映射到设备粒度 | 注意力式时间因果发现能否恢复传播边及其时延？ | Graph-only 外部方法；不输出根因排名，Root/Full-Graph 为 `X` |
| Our Stage 2：P0 | 相同根/候选域/目标，使用完整局部支持与根条件路径搜索/合并 | 本文传播重构效果 | 本文方法 |

固定根因使用两套独立设置：①所有图方法都使用 PC-STGR OOF 预测 Top-1；②所有图方法都使用真实单根标签作 Oracle-root 控制实验。第二套标签只能由离线评测包装层传入，并单独标记；不得与无标签推理混在同一主结果中。Oracle 表控制根错误，不预设它是所有实际输出指标的数学上界。

图指标：有向边 P/R/F1、节点 P/R/F1、整图匹配、图规模及相关目标覆盖；拓扑合法率、根可达率与无环率作为单独有效性指标。原始设备粒度与结构等价投影口径分开报告。没有输出的图或无法解释的目标保留为失败/部分解释，不因其拉低分数而剔除案例。

全流程比较中，可把各外部根因排序器的候选根分别接到同一个 P0，命名为“外部 Root + P0”，评价替换根阶段的效果；这不代表外部论文自身具备 P0 的图恢复能力。固定根图表用于独立评价 C2/C3，不能只报告全流程根准确率。

## 3. NetEventCause 到设备图的适配规则

NetEventCause 是最关键的外部传播对照，不能直接拿事件 DAG 与设备 DAG 算 F1，也不能给它接上 P0 解码器后把结果当作原方法的传播输出。

1. 从原模型保留事件实例 ID、所属设备、时间、根分数、候选事件边和可用归因分数；事件到设备的映射只能来自输入归属。
2. 同设备事件边保留在事件层，设备图中不输出自环。跨设备同方向多条边第一版取最大归因支持；若作者接口只有边而没有可比归因分数，则使用明确的二值支持，不编造概率。
3. 先保存未经物理筛选的设备投影，统计非邻接边、双向冲突、环与根不可达关系；不把这些边作为满足本文物理边契约的最终设备传播输出。
4. 主表适配版仅保留原始物理邻接上的边，不将非相邻事件关系自动补成一条最短路径；这种补全会引入另一个推断模块。删除指向给定根的边，按支持降序和固定 ID 顺序加入不产生环的边，再保留从根可达的部分。明确命名为“NetEventCause-Device + greedy adapter”。
5. 同时报告适配前后的方向冲突/结构有效性变化与丢弃边比例；适配前仅作受控评测诊断，不作为合法图发布。不会在推理中查标签决定删哪条边。

即使事件图无环，设备聚合也可能产生环，例如 `A事件1→B事件1→A事件2` 在设备层成为 `A→B→A`。因此，原模型已采用 DAG 与设备输出仍需适配并不矛盾。上述规则是本实验新定义的适配，不是原作者算法的能力主张。

## 5. 公平比较的固定协议

- **相同案例与单根口径。** 所有主表使用同一 incident 清单、同一根标签和传播图标签版本；不混入早期不同标签或投影规则的分数。
- **按 incident 分组。** 学习式方法、事件词表、归因门限、权重开发、少样本检索和提示更新均限制在当前外层训练 fold；未标注的测试事件也不能用来拟合模型后再称 OOF。推理时观察当前案例的输入与用它训练模型是两回事。
- **候选和目标一致。** 根表使用同一可选设备集合；图表使用同一候选物理图和相关目标。不要把 P0 专用边评分/筛选预先喂给所有外部模型；外部 Root + P0 只作为单独的全流程敏感性分析。
- **缺失不等于否定。** 没有事件、没有 SOP、没有路径字段分别保留为缺失；不能用正常样本、无传播标签或伪造工单填补。
- **知识与监督透明。** PC-STGR 使用根标签，P0 不用图标签训练局部支持；外部模型的历史训练、SOP、检索知识与本地模型预训练条件分别列出。输入较多/较少时报告差异，不声称完全同信息。
- **本地推理。** 本项目 LLM 实验仅使用本地 vLLM/Ascend 资源；固定模型、token 预算与温度。不使用 mock/fallback 输出冒充已运行模型。
- **未决与部分标注。** 未知关系按评测协议 mask；部分图的未知边不能直接当负例。案例置信区间按 incident 重采样，而不是将设备边当独立样本。
- **性能之外报告开销。** 记录训练成本和每例推理时延；在可比较条件下报告内存/模型预算、输出图大小、失败率与候选召回。

## 7. 实施顺序与本轮交付边界

1. 冻结统一案例、单根标签与 grouped folds；记录现有代码版本，避免把旧分数直接拼入新表。
2. 完成 SkyNet-inspired Alert Voting、NetRCA-adapt、PCMCI+/DYNOTEARS/TCDF 和其他外部图候选的输入审计，先确定每个任务列是否可测。
3. 接入并核对原 NetEventCause，完成训练侧拟合、事件输出、设备投影与图适配；这是最重要的外部图对照。
4. 按原文补齐 BiAn 可由当前输入支持的关键机制；Pipeline1 单列。随后优先补 REASON/CORAL 的图输出审计和 NetCause-adapt 强学习式定位比较。Graph-only 方法只进入 Oracle-Graph，不接根因头。
5. 在相同预测根及 Oracle 根条件下形成图表，再报告各根排序器加同一 P0 的全流程结果。

本轮完成的是相关工作文字、基线选型与可执行比较协议；尚未新增训练、推理或性能结论。当前实现的差异已经记录，后续结果必须使用修正并明确命名的版本。
