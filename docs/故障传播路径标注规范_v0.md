# 故障传播路径工程师标注规范 v0

更新日期：2026-08-11  
状态：试标草案，待 5–10 个 case 试标后修订

## 1. 标注目标

为 Pingmesh 故障 case 建立可复核的设备级传播真值，支持后续严格匹配、结构指标、Top-K 指标及容错/舍入准确率等多种评价方式。

主标注对象是设备级传播 DAG。告警、日志、接口和对端信息只作为节点/边证据，不作为主图节点。

传播方向统一为：

```text
根因设备/根因链路端点 -> 中间传播设备 -> 受影响设备/症状
```

## 2. 标注输入包

每个 case 向标注工程师提供：

- 匿名化 case ID；
- Pingmesh source、sink、触发时间和异常类型；
- 本 case 的物理拓扑子图；
- 设备角色和上下游/邻接关系；
- 经过归一化的告警事件片段；
- 原始告警/日志的只读下钻入口；
- 接口、对端设备、BGP peer、LLDP remote、local/remote fault 等抽取字段；
- 必要时提供事故复盘或工单证据。

不向标注工程师展示待评价算法的传播结果，以减少锚定偏差。若需要让工程师修订算法结果，应作为独立的工程可用性实验，不与真值标注混用。

## 3. 标注单位

### 3.1 节点

节点必须是物理网络设备。每个节点标注：

- `device_id`：匿名设备标识；
- `role`：`root / root_endpoint / propagation / affected / uncertain`；
- `membership`：`definite / possible / excluded`；
- `onset_interval`：可确认的异常开始时间区间，无法确定时留空；
- `evidence_ids`：支撑该节点角色的证据；
- `note`：必要的人工说明。

其中 `root_endpoint` 用于根因实体是设备间链路的情况。此时两个端点可以同时是根因边界，但不能因此假定两个设备自身都发生独立设备故障。

### 3.2 边

边表示本 incident 中一个设备对另一个设备的候选影响传播关系。每条边标注：

- `from`、`to`：根因到症状方向；
- `membership`：`definite / possible / impossible`；
- `relation`：`physical_link / control_plane / routing_convergence / inferred_impact / unknown`；
- `direction_status`：`confirmed / likely / unresolved`；
- `lag_interval_ms`：可确认的传播时延区间，无法确定时留空；
- `evidence_ids`：支撑该边的证据；
- `alternative_group`：与哪些边构成 ECMP 或证据不足导致的等价选择；
- `note`：必要的人工说明。

只因两个设备同时告警、告警名称相似或在拓扑上相邻，不能直接标成 `definite` 边。

### 3.3 根因作用域

根因作用域单独标注为：

- `device`：根因可定位到单台设备；
- `inter_device_link`：根因位于两个设备之间的物理链路；
- `multiple_devices`：确有多个独立或联合根因设备；
- `uncertain`：现有材料不足以区分。

当根因是链路时，记录 `root_link`，并把两个端点标为 `root_endpoint`。设备级 DAG 仍只包含设备节点，根因链路作为图的元数据和特殊边保存。

### 3.4 可诊断性

每个 case 必须选择：

- `fully_observed`：现有证据足以给出一组明确的设备传播边；
- `partially_observed`：部分边明确，其余只能给出候选或等价分支；
- `unidentifiable`：现有材料不足以形成可评价的传播图；
- `out_of_scope`：并非设备/链路传播问题，或混入多个无法拆分的 incident。

## 5. 标注步骤

1. 确认 case 是否为单一 incident，判断是否 `out_of_scope`；
2. 确定根因作用域是设备、链路、多设备还是不确定；
3. 只根据证据选择 definite 节点，不追求覆盖所有告警设备；
4. 沿根因到症状方向逐条添加 definite 边；
5. 对合理但无法唯一确定的边标记 possible，并建立 alternative group；
6. 对容易被算法误选但证据明确排除的关键边标记 impossible；
7. 为每个节点和边绑定 evidence ID；
8. 标记可诊断性和总体置信度；
9. 由第二名工程师独立重复上述过程；
10. 对分歧 case 进行仲裁，保存仲裁前和仲裁后的版本。

## 6. 证据使用规则

### 6.1 可以作为强证据

- 事故复盘明确记录的故障设备、链路和影响关系；
- 设备接口与对端接口能相互对应的 local/remote fault；
- 明确引用对端设备或 peer 的 BGP、LLDP、链路状态事件；
- 多源证据在拓扑、相对时间和语义上相互支持；
- 维护操作、硬件更换或恢复动作能验证故障位置。

### 6.2 只能作为弱证据

- 单纯时间接近；
- 单纯设备相邻；
- 相同告警模板在多台设备出现；
- 告警数量多或严重度高；
- PageRank、时序 ranker 或 LLM 给出的高分。

弱证据可以支撑 `possible`，不能单独支撑 `definite`。

### 6.3 不应作为真值依据

- 待评价算法输出；
- 无法追溯到输入的自然语言推断；
- 仅凭设备角色或经验先验强制补全的边；
- 为了得到单条完整链而人工填补的未知中间边。

## 7. 歧义处理

### ECMP 或多条等价路径

保留所有可接受分支并放入同一 `alternative_group`。不要随机选择一条作为唯一真值。

### 告警时间倒序

先检查采集延迟、聚合窗口、active/clear 配对和设备时钟。若仍无法解释，保留时间区间并把方向标为 `likely` 或 `unresolved`，不要只按最早告警定因果方向。

### 共同上游导致的同时异常

两个设备同时异常不代表二者互相传播。若更可能是共同上游影响，应避免添加二者之间的传播边。

### 根因是链路

使用 `root_scope=inter_device_link` 和两个 `root_endpoint`。不要为了符合单设备根因格式随意选择其中一端。

### 多个 incident 混叠

能拆分时分别标注；不能拆分时标为 `out_of_scope` 或 `unidentifiable`。

## 8. 质量控制

试标阶段建议：

- 先选 5–10 个涵盖设备根因、链路根因、ECMP、长链和告警风暴的 case；
- 两名工程师独立标注，第三人仲裁；
- 统计根因作用域一致率、节点 Jaccard、边 Jaccard、方向一致率和 diagnosability 一致率；
- 记录每个 case 的标注耗时和主要分歧原因；
- 若 definite 边一致性偏低，优先修订定义和证据规则，不急于扩大到 30–50 个 case；
- v0 规范通过试标后冻结为 v1，再开始正式标注。

## 9. 与评价指标的解耦

标签应保存原始的 definite、possible、impossible 边及可接受假设，不在标签中写入某个评价公式的得分。

评价脚本后续可以配置：

- strict：只接受 definite 边和完全匹配；
- tolerant：允许 possible/alternative 边，并以相似度阈值判定 case 正确；
- rounded accuracy：对相似度统一舍入后再与阈值比较；
- component：分别计算根因、节点、边、顺序和证据指标。

任何舍入位数、容忍阈值和相似度权重都必须版本化，并在测试集解封前确定。

## 10. 数据隔离要求

- 路径标签只能出现在评估、标注和诊断目录；
- 推理代码不得读取本标签；
- 不把内部设备 IP、原始告警描述、case ID 或工程师身份写入论文和公开仓库；
- 公开示例使用匿名设备和经过脱敏的证据片段。
