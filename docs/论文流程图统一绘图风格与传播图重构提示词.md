# 论文流程图统一绘图风格与异构传播图重构提示词

## 1. 固定视觉风格

使用适合 INFOCOM/NSDI/SIGCOMM 论文的黑白单线工程示意图。背景为纯白，主体使用深灰描边和黑色文字；仅用低饱和蓝色表示观测与证据，用低饱和紫色表示概率关系，用低饱和橙色强调最终传播图。模块采用轻圆角矩形，候选或证据集合采用虚线边框，主流程箭头自左向右且方向清楚。避免渐变、阴影、3D、卡通图标、大面积填色和密集装饰。

文字使用简洁无衬线字体，所有标签保持水平。全图只展示 M1、M2、M3 三个方法模块，不出现 PC-STGR、IC-STGR、旧 Stage 1/Stage 2、根因重排或旧的四模块设备级流程。

## 2. 方法总览图提示词

Create a publication-ready black-and-white monoline system diagram for a data-center-network paper. Use a pure white background, dark gray strokes and labels, sparse muted blue accents for observations and evidence, muted purple accents for uncertain probabilistic relations, and muted orange accents for the final reconstructed explanation graph. Arrange the content from left to right as inputs, three numbered method modules, and outputs.

On the far left, place three compact input groups: “Pingmesh Symptom Context”, “Raw task_topo Physical Topology”, and “Alarms, Logs, and Timestamps”. Use blue accents for these observed inputs. Do not depict any input relation as a known causal edge.

Module 1 is “M1 Evidence Modeling and Candidate Heterogeneous Graph”. Inside it, show three visually distinct node types: square “Device”, circle “Event”, and hexagon “Symptom”. Show typed candidate/evidence relations: solid gray undirected “Physical adjacency” between devices, blue “Observed on / ownership” between a device and an event, blue “Endpoint association” between a device and a symptom, and dashed gray “Candidate dependency” between events. Add small labels for “Episode normalization”, “Endpoint corridor”, “Event-bearing devices”, and “Necessary connectors”. Make clear that this graph only defines the candidate search space and evidence context.

Module 2 is “M2 Heterogeneous Relation Learning”. Draw a compact relation-aware graph encoder followed by exactly three output heads. The first is “Root Potential” over device nodes and virtual link-root candidates. The second is “Device Relation: A → B / B → A / No Direct Propagation”. The third is “Event Relation: Ei → Ej / Ej → Ei / No Dependency”. Use purple semi-transparent or dashed arrows to form a “Probabilistic Heterogeneous Graph H”. Show that competing directions and ambiguous branches may coexist. Do not feed a chosen root identity into the device-relation head, and do not turn local probabilities directly into the final graph.

Module 3 is “M3 Joint Root-and-Graph Constrained Reconstruction”. Feed it the probabilistic graph, raw-topology constraints, and evidence-coverage requirements. Show an optional dashed experimental input labeled “Oracle Root (Evaluation Only)”. Add compact constraint badges: “Raw-topology Valid”, “Single Direction”, “Root Reachable”, “Acyclic”, “Symptom Covered”, and “Evidence Consistent”. Indicate joint optimization over the root, selected device edges, selected event relations, and covered symptoms. Add a small side output labeled “Top-K Near-optimal Explanations”.

On the far right, make the final heterogeneous explanation graph the visual focus. Use a thick orange directed Device → Device DAG as the primary backbone. Mark one orange source as “Root Device / Root Link”. Attach a smaller event-evolution chain to the corresponding devices using thin blue observation/ownership links. Visually separate and label the three relation layers: “Device Propagation DAG (Primary)”, “Event Evolution / Dependency (Explanation)”, and “Device–Event Evidence Grounding (Observed, not causal)”. Add four compact result fields: “Confidence”, “Evidence Trace”, “Alternative Hypotheses”, and “Identifiability / Abstention”.

The figure must communicate one main task: reconstruct an evidence-grounded heterogeneous fault-propagation graph while jointly identifying its root. Root ranking must not appear as a mandatory upstream stage. Physical adjacency, ownership, temporal order, and alarm semantics must be shown as circumstantial evidence rather than deterministic propagation.

## 3. 图中建议标签

### 输入

- Pingmesh Symptom Context
- Raw task_topo Physical Topology
- Alarms, Logs, and Timestamps

### M1 输出

- Candidate Heterogeneous Evidence Graph `G_c`
- Device / Event / Symptom
- Physical / Observed-on / Endpoint / Candidate-dependency

### M2 输出

- Root Potentials
- DD Three-state Probabilities
- EE Three-state Probabilities
- Probabilistic Heterogeneous Graph `H`

### M3 输出

- Root Device or Root Link
- Device Propagation DAG
- Event Evolution Explanation
- Evidence Grounding
- Top-K Alternatives
- Identifiability / Abstention

## 4. 推荐图注

**异构故障传播图联合重构方法总览。** 系统首先将 Pingmesh 症状、原始物理拓扑与告警日志建模为设备—事件—症状候选异构图；随后学习设备/链路的根因势能、设备对的三状态传播概率及事件对的三状态依赖概率；最后在拓扑合法、根可达、无环、症状覆盖和证据一致约束下，同时识别根因并恢复设备传播 DAG 与事件解释层，同时保留近最优替代假设和不可辨识状态。

## 5. 复核清单

1. 全图必须只有 M1、M2、M3 三个主模块；
2. 根因是 M3 的联合输出，Oracle Root 只能以“评价模式”的虚线输入出现；
3. 最终设备传播 DAG 必须是主视觉对象；
4. 必须区分设备传播、事件依赖/演化和设备—事件证据归属三类关系；
5. 必须区分原始物理边、候选关系、概率关系和最终传播边；
6. 不把时间先后、拓扑相邻、事件归属或告警语义直接画成确定因果；
7. M2 概率图可以显示冲突方向或不确定分支，M3 输出必须全局一致；
8. 每条最终设备传播边可回溯到原始 `task_topo`，每个解释事件可回溯到原始告警/日志；
9. 输出应包含替代假设与 identifiability/abstention，而不是被迫给出唯一确定图；
10. 不出现旧的两阶段排序叙事、PC-STGR 主流程或根因加权重排公式。
